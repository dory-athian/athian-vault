Making CE artifacts survive session boundaries

Planning and ideation outputs at Athian are created locally, never routed, and invisible to the team. These 7 ideas target the structural gaps — storage, context composition, continuity, discoverability, and artifact lifecycle — with a bias toward choices that compound over time.

7 ideas — pipeline nodes — ranked by compounding potential

The Canonical Session Payload Schema

Session continuity direct:

Define a single JSON schema — call it ce-session.schema.json — that any CE Stop hook can emit: run-id, timestamp, repos touched, artifact paths, axis tags derived from the YAML frontmatter vocabulary already in docs/solutions/, and a one-line summary. Today there is no standard payload; whoever owns this schema first owns the routing layer for every future CE session across every repo. The Feedback Hub's 22-column schema proved this team can maintain a structured schema in production — apply the same discipline here.

Why it matters Owning the schema is owning the bus: every downstream tool — n8n routing, Linear issue creation, CLAUDE.md auto-loading — becomes a consumer of one stable contract rather than a bespoke integration.
Meeting test "Can we add a new routing destination for CE sessions without touching the hook itself?" — yes, if the schema exists; no, if it doesn't.

HANDOFF.md Machine-Readable Header

Artifact lifecycle direct:

Every HANDOFF.md already gets written at session close. Add a YAML front-matter block — matching the module / tags / problem_type vocabulary already established in docs/solutions/ — plus two new fields: status: draft | review | filed and linear_issue:. The file stays human-readable; automation now has a stable parse target. A PostToolUse hook on Write fires whenever HANDOFF.md is saved, reads the front-matter, and routes based on status. The existing YAML vocabulary is the leverage point: this extends a schema the team already knows rather than inventing a new one.

Why it matters One field change (status: filed) becomes the trigger for Linear issue creation, Slack notification, and docs indexing — the document's own header drives its lifecycle.
Meeting test "How do we know when a HANDOFF is ready to become a ticket?" — the status field answers; right now nobody knows.

Cross-Repo Docs Repo as the Neutral Home

Storage location reasoned:

Create a third repo in the Athian-ai org — call it athian-ai/docs — that is the canonical home for all CE outputs: ideation, brainstorms, plans, and HANDOFFs. Both platform and sus-plat have CLAUDE.md files that can reference it via the @ import mechanism already established in the CLAUDE.md hierarchy. Today, cross-repo planning docs have no neutral home; they live on whoever's machine ran the session. A dedicated docs repo also gets GitHub-native discoverability: search, permalinks, and PR-driven review — without requiring any new tooling.

Why it matters Every future CE session that touches either repo can reference prior plans by URL rather than filename-on-disk; the repo becomes the team's institutional memory rather than a local scratch directory.
Meeting test "Where does the plan Dory wrote last week live?" — right now: unknown. With this: a GitHub URL anyone on the team can open.

CLAUDE.md as a Deliberate Composition Layer

Context hierarchy direct:

The @voice/ import pattern already works in the global CLAUDE.md — it composes context from named files. Apply this deliberately to engineering context: the root /Athian/CLAUDE.md imports @docs/ACTIVE_PLAN.md (the current cross-repo plan) and @docs/OPEN_HANDOFFS.md (a generated index of unresolved HANDOFFs). Repo-level CLAUDE.md files inherit this and add repo-specific overlays. Every CE session in any repo automatically loads the current plan as grounding — without the user having to paste it. This is not a new mechanism; it's deliberate design of a hierarchy that already exists but isn't being used intentionally.

Why it matters Every CE session across any repo starts with the current plan in context automatically; the cost of "loading grounding" drops to zero and stays there.
Meeting test "Does Claude know what we were planning last week when I start a new session?" — with deliberate CLAUDE.md composition, yes; without it, no.

PostToolUse Hook as the Universal Capture Layer

Session continuity direct:

The PostToolUse hook in .claude/settings.json fires after every Write from Claude Code. Configure it to watch for CE artifact filenames — HANDOFF.md, docs/ideation/*.html, docs/plans/*.md — and on match, emit a structured JSON event (following the canonical schema from Idea 1) to a local queue file or directly to an n8n webhook. This is one hook, one pattern match, one emit — but it fires on every future CE session across every repo that loads this settings file. The capture layer compounds silently: every session adds to the index without anyone remembering to do it.

Why it matters Capture happens at the point of creation, not as a separate filing step — which means it actually happens, every time, at zero marginal effort.
Meeting test "Did this session's artifacts get indexed?" — with the hook: always; without it: only when someone remembers to file them.

The CE Artifact Index as a Living Google Sheet

Discoverability reasoned:

The Feedback Hub already routes Granola → n8n → Google Sheets → Claude. Reuse the same pipeline: CE artifact events (from the PostToolUse hook) flow through n8n into a second sheet — same infrastructure, different columns. Columns: artifact type, subject, axis tags, repo, session date, artifact path or GitHub URL, status, linked Linear issue. Claude can then answer "what have we planned about auth in the last 60 days?" by querying this sheet exactly as it queries the Feedback Hub. Discoverability becomes a natural language query rather than a file system search.

Why it matters The trusted infrastructure is already proven and maintained; the marginal cost of a second sheet is near zero, and the team already knows how to query it.
Meeting test "What CE sessions have touched the emissions calculation module this quarter?" — answerable in 30 seconds if the index exists; not at all if it doesn't.

Prior-Session Grounding via Index Lookup at Session Start

Session continuity reasoned:

Once the CE artifact index (Idea 6) and the canonical schema (Idea 1) exist, a PreToolUse hook on Task launch — or a CLAUDE.md injected snippet — can query the index for recent sessions on the same subject and inject a "prior context" block into the session grounding automatically. The sub-agent does not need to be told "we planned this last week"; it loads it. This is the second-order payoff of building the index: future sessions get smarter without any additional user action. Each session captured makes the next session cheaper to orient.

Why it matters Planning sessions stop re-discovering the same ground; accumulated decisions carry forward automatically, compounding the value of every past session.
Meeting test "Does this session know what we already decided about the HANDOFF format?" — yes, if the index lookup fires at start; no, if not.

Ideas considered and cut

Git-tracked local docs Still invisible to the team unless pushed; adds a commit step that won't always happen. Doesn't solve discoverability.
Per-session Slack DM summary Creates noise without structure. Slack is not searchable by axis or module. Works as a notification layer on top of an index, not as the index itself.
Linear for all CE artifact tracking Linear is the right place for filed work items, not raw ideation. Pushing every brainstorm into Linear creates noise in the issue tracker and conflates planning with execution.
Shared network drive / Dropbox Solves storage but not discoverability, lifecycle, or session grounding. No metadata, no queryability, no integration with the existing toolchain.
