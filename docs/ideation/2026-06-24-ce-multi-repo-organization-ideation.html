Key Pain Points

Confirmed Mechanics

  • Planning Repo Pattern: parent git repo .gitignores nested repos — well-documented community pattern

External Patterns Surveyed

All four major patterns agree: cross-repo planning docs live at the workspace/meta level, CLAUDE.md files layer hierarchically, and session continuity is a recognized problem solved by committable plan files.

1
The Workspace Root Becomes the Repo
Storage location High confidence · 95% Complexity: Low
Description

Run git init in /Athian/ and add a .gitignore that excludes the nested repos under projects/. CLAUDE.md, STRATEGY.md, HANDOFF.md, docs/, and all CE outputs that already land there become tracked, versioned, and pushable to GitHub with a single commit. The child repos (platform, sus-plat, duita) remain independent git repos, untouched. This is the Planning Repo Pattern applied to existing reality.

Basis
direct: /Athian/ already contains CLAUDE.md, STRATEGY.md, HANDOFF.md, and docs/ with 20+ CE artifacts — all confirmed untracked. The Planning Repo Pattern (external research) documents exactly this setup: "parent git repo that .gitignores all nested repos."
Rationale

Zero workflow change. Nothing about where CE outputs land needs to change — the directory structure, the docs path, the session habits all stay identical. The only delta is a git init, a .gitignore, and a GitHub remote. Every artifact produced over the past month becomes tracked in one commit. Claude Code's directory-walk loading already makes this the natural context root — formalizing it into a git repo makes it the team's shared source of truth.

Downsides
The workspace repo and the product repos are on separate git histories — cross-repo changes (e.g., a plan doc and its corresponding code) live in different commits. Discipline required to not accidentally commit large files (ideation HTMLs are fine; raw PDFs are not). Engineers who clone only the product repos won't see workspace docs without a separate clone.
2
Three-Tier CLAUDE.md Hierarchy
CLAUDE.md / context hierarchy High confidence · 90% Complexity: Low
Description

Formalize the workspace CLAUDE.md at /Athian/CLAUDE.md as the deliberate middle tier between the global (~/.claude/CLAUDE.md) and per-repo files. The workspace layer owns: org context (team roster, repo map, active cross-repo projects, shared tool conventions). Per-repo files own: stack-specific architecture, domain models, commands, patterns. Claude Code's directory-walk loads these in order from root to CWD — the missing piece is treating the workspace layer as authoritative infrastructure, not an incidental landing file.

Basis
direct: sus-plat and duita both have CLAUDE.md files with repo-specific arch docs. /Athian/CLAUDE.md exists but is untracked and has no defined workspace role. external: Spine Pattern three-tier hierarchy and the official Claude Code docs both document this exact load order: global → project → per-directory.
Rationale

Right now cross-repo context either lives in your head or gets re-explained from scratch at each session start. A stable workspace CLAUDE.md means every Claude Code session — on any repo, by any engineer — opens with the org map already in context. The compounding value: as you add repos, each adds one CLAUDE.md; the workspace layer gets one pointer. Second-order effect: every engineer's AI sessions benefit from it automatically, without any additional setup per-developer per-repo.

Downsides
Requires discipline to keep the three tiers non-redundant — content that lives in the workspace layer should not be duplicated in per-repo files. The workspace CLAUDE.md loads for every session regardless of which repo you're working in, so it shouldn't grow too large (target under ~150 lines). A team unfamiliar with the three-tier model may not know where to add new instructions.
3
repos: Frontmatter on CE Outputs
Discoverability High confidence · 90% Complexity: Low
Description

Extend the existing docs/solutions/ YAML frontmatter convention — which already uses module, tags, and problem_type — by adding a repos: field to CE planning and strategy outputs. Every plan doc, ideation artifact, and strategy memo declares which repos it touches: repos: [duita, sustainability-platform]. A second field, status:, tracks lifecycle state (see idea 4). A five-line shell script can then list every artifact that touches a given repo. No new directories, no new conventions, no tooling required on day one.

Basis
direct: docs/solutions/ YAML frontmatter is confirmed working — the field structure (module, tags, problem_type, etc.) is already in use. The Nestle pilot is a real, named cross-repo case spanning duita and sus-plat with no current ownership anchor. Extending an existing pattern requires no adoption friction — the team already reads and writes this frontmatter.
Rationale

The cross-repo ownership problem — "where does this plan live when it spans two repos?" — is solved without choosing a structural answer. Plans stay in docs/; frontmatter declares scope. The second-order effect: once repos: exists, a simple script can generate a per-repo index of all plans that touch it, surfacing cross-repo context automatically during onboarding or project kickoffs. Zero tooling required on day one; tooling becomes optional later.

Downsides
Only as good as the discipline to fill it in. repos: fields can go stale if plans pivot scope mid-execution. Doesn't help a new engineer find plans they don't know exist — relies on either a generated index (not yet built) or knowing to grep frontmatter. HTML ideation artifacts (like this one) don't carry YAML frontmatter natively, so the convention applies mainly to markdown plan and strategy docs.
4
CE Output Status Lifecycle
Artifact lifecycle High confidence · 88% Complexity: Low
Description

Add a status: field to CE output frontmatter with four states: draft (plan exists, work not started), in-progress (work underway, Linear/Jira issue open), shipped (work done, code merged), archived (superseded or abandoned). A generated index of all non-archived docs — producible by a simple script or a CE hook — becomes the engineering team's living roadmap and release record. The "what did we ship and why" question, which currently requires a Slack archaeology dig, has an answer.

Basis
direct: docs/solutions/ YAML frontmatter infrastructure already exists — a status: field requires no new tooling. The "what did engineering ship" question is a real, recurring need from Sales, Customer Success, and the board. reasoned: Status as frontmatter means a plan in in-progress that stays there too long becomes visible without any process overhead.
Rationale

CE outputs stop being planning debris and become a live engineering record. The promoted shipped docs answer the recurring "what's new" question for non-engineering stakeholders without requiring anyone to translate Linear tickets. Works in tandem with idea 3: a plan doc with both repos: and status: is queryable two ways — by which repos it touches and by where it is in its lifecycle.

Downsides
Requires a human to update the status field as work progresses — it won't self-update. In practice, in-progress plans may sit stale after the sprint ends. The index is only as accurate as the last time someone ran the generation script. Works better as a lightweight convention than a formal process.
5
Committed Session Checkpoints
Session continuity High confidence · 85% Complexity: Low
Description

When a CE session ends, copy the V17 checkpoint file (which CE writes to /tmp/compound-engineering/...) into the workspace repo under _sessions/YYYY-MM-DD-<slug>.md and commit it. The checkpoint captures the full session state: active grounding, candidate ideas, decisions made, open questions, next steps. Opening it in the next session re-establishes context without re-running Phase 1 grounding. Plan docs in docs/ link to their checkpoint via a session_id: frontmatter field. HANDOFF.md becomes a pointer to the most recent committed checkpoint, rather than the checkpoint itself.

Basis
direct: HANDOFF.md exists as a single, manually-maintained session log — confirmed as the current continuity mechanism, limited to one concurrent session and untracked. CE V17 checkpoints are already written to /tmp/ during sessions. external: Spine Pattern explicitly uses _tasks/ files as resumable artifacts to survive session boundaries.
Rationale

Session context becomes as durable as code. When a second engineer picks up a cross-repo plan, they don't start from zero — they open the checkpoint and resume. This is the highest-leverage answer to the session continuity problem without requiring new tooling beyond a copy command and a commit. Works especially well for the Nestle pilot pattern: one long-running cross-repo initiative with multiple CE sessions across multiple weeks.

Downsides
Requires a two-minute copy-and-commit step at the end of each meaningful CE session — likely to be skipped when sessions end abruptly. Checkpoint files are verbose (full grounding, raw candidate lists, phase notes) and may accumulate quickly. The _sessions/ directory could become noisy without a cleanup convention for old sessions.

Dedicated GitHub Workspace Repo
Storage location Medium confidence · 72% Complexity: Medium
Description

Create athian-ai/athian-workspace (private) as a dedicated orchestration repo with no application code. It holds: a root CLAUDE.md, docs/ for cross-repo plans and decisions, _sessions/ for CE checkpoints, .claude/skills/ for cross-repo skills, and a scripts/setup.sh that clones all child repos into a sibling directory and reconstitutes the full workspace. Any engineer can run ./scripts/setup.sh to get a working cross-repo development environment in minutes. This is a more structured, explicit version of idea 1.

Basis
external: Meta-Repo / Repo-of-Repos pattern and Spine Pattern both document this structure with clone scripts (e.g., a .repos script that clones all repos). direct: /Athian/ is the natural working root and already serves this role informally — formalizing it as a GitHub repo makes it team-accessible and cloneable.
Rationale

The clone script is the key differentiator from idea 1. It means a new engineer — or an engineer picking up an unfamiliar repo — can reconstitute the full cross-repo development context in minutes rather than figuring out which repos to clone and where to put them. Positioning it as a genuine GitHub repo rather than just a local git init makes it more sustainable as the team grows and as the repo count increases past three.

Downsides
More setup than idea 1 — requires creating the GitHub repo, writing the clone script, and establishing the convention across the team. The clone script needs maintenance as repos are added. Medium complexity relative to idea 1's near-zero effort. May feel like over-engineering at three repos. Ideas 1–5 can be implemented first and this can be a natural evolution once the patterns are established.
7
Cross-Repo Skills in workspace/.claude/skills/
Storage location Medium confidence · 70% Complexity: Low
Description

Establish /Athian/.claude/skills/ (or the workspace repo's .claude/skills/) as the canonical location for Claude Code skills whose scope spans multiple repos. Per-repo skills stay in each repo's .claude/skills/. The workspace CLAUDE.md registers all active cross-repo skills explicitly. The immediate candidate: the add-protocol-skill, which ingests a PDF and scaffolds code across both platform and sus-plat, currently has no declared home.

Basis
direct: add-protocol-skill is an active project listed in the workspace CLAUDE.md as an active project with no declared location. /Athian/.claude/ already exists with settings.json. reasoned: Skills with cross-repo scope don't belong in any single product repo's .claude/ — that would imply ownership by one repo over work that spans both.
Rationale

Resolves the ownership ambiguity for the add-protocol-skill immediately and establishes a pattern for any future multi-repo agents. Every future skill whose scope isn't bounded by one repo (the Feedback Hub Claude query interface, future protocol skills) has a declared home. The workspace CLAUDE.md's registration of cross-repo skills also makes the full AI toolset discoverable to every engineer at session start.

Downsides
Depends on idea 1 or 6 — the workspace directory needs to be a git repo first for this location to be tracked and shared. Without that, the skill lives on one person's local machine, which is the problem we're solving. Small surface area compared to ideas 1–5, but unlocks naturally once the workspace repo exists.

Rejection Summary

Idea Reason Rejected
A3 · _plans/ Frontmatter Directory Duplicates idea 3 (B3). B3 is strictly stronger — it extends the existing docs/solutions/ pattern rather than creating a parallel directory that splits the information architecture.
A5 · docs/decisions/ ADR Store docs/solutions/tooling-decisions/ already exists (verified: the Linear MCP skills decision is filed there). A second decisions directory would fragment what's already working. The existing YAML frontmatter is flexible enough to encode decision types.
A7 · repo-map.md Living System Diagram The workspace CLAUDE.md (idea 2) already serves as the system map, and per-repo CLAUDE.md files contain repo layout. A third document for the same information creates drift without adding surface area.
B2 · CLAUDE.md as Auto-Updated CE Index The auto-update premise introduces write-contention on a file Claude Code loads at session start. The navigation value is real but better served by a separate index file generated on demand, not by polluting the always-loaded context file.
B4 · Session Continuity via Git Commits Refuted: replacing HANDOFF.md with git commit history degrades the primary use case — HANDOFF.md is directly readable by Claude Code at session start, whereas hunting through commit messages for session context is strictly worse UX. Idea 5 (committed checkpoint files that remain directly readable) is the correct fix.
B5 · CE Outputs as Primary Artifact (plan_ref: in commits) Cultural intervention requiring team enforcement this org doesn't have bandwidth for. plan_ref: in commit messages is hard to query and easy to omit. The why-documentation problem is better addressed by ideas 3 and 4 (frontmatter and status lifecycle) than by restructuring commit conventions.
B6 · Collapse Per-Repo CLAUDE.md into One File Refuted: Per-repo CLAUDE.md files contain repo-specific architecture that is only useful when Claude Code is working inside that repo. Collapsing into one file means every session loads all repos' architecture regardless of CWD — wastes context window and actively undermines Claude Code's scoped loading model, which is designed to deliver narrowed context.
B7 · repos.yaml Machine-Readable Manifest Premature at three repos. A YAML manifest only pays off when tooling consumes it, and no such tooling is described. The discovery problem it solves doesn't exist yet at this org's scale. Worth revisiting past five repos.
