The prior ideation pass (2026-06-23 — same day) covered the planning-repo, spine, and lifecycle-trigger ideas. Those are the pattern-matching answers. These ideas cut against what that run treated as given: that artifacts need repos, that persistence requires saving, that the team finds things by searching, that the session boundary is the unit of continuity.

Each idea is generated from one of two frames: an assumption being treated as fixed, or a constraint inverted to its extreme. Basis tags reference the grounding document directly.

Ideas — 7 survivors
01
Assumption-breaking Constraint-flipping: storage

Linear is the repo. Kill the docs/ directory for planning.

The assumption: planning artifacts belong in a repo. The flip: Linear already is a structured, version-controlled, cross-repo planning layer — with documents, projects, milestones, and a rich text editor. The constraint "must be in a repo" exists because the team wants planning artifacts version-controlled and findable. Linear satisfies both, plus it surfaces to the whole team automatically. Rather than creating a planning repo with _plans/ and frontmatter, write CE planning outputs directly into Linear documents attached to the relevant project (e.g., "Nestle Pilot" project in Linear). The artifact lives where decisions get acted on, not in a directory no one opens unless they know to look.

Axis
storage location · discoverability
Basis
direct: Jira → Linear migration active; Linear MCP server in use. reasoned: Linear documents are already the planning layer the team uses — adding a parallel repo-based system doubles storage without adding coverage.
Assumption broken
"Planning artifacts belong in a repo" — actually they belong where the team acts on them. Linear is that place at Athian now.
Constraint flipped
Budget from 0 to 10x: if you had 10x the tooling budget, you'd buy a dedicated planning layer. You already own one. The repo is the code; Linear is the plan.
Meeting test

"Why do we have a docs/ directory for things that aren't documentation?" — if no one can answer that without defending inertia, this idea wins the room.

02
Assumption-breaking

Abolish docs/. CLAUDE.md files are the only documentation system.

The assumption: AI context (CLAUDE.md) and planning artifacts (docs/) are different things. They are not. A planning artifact that doesn't end up in a CLAUDE.md gets read once and forgotten; a CLAUDE.md entry gets included in every subsequent session automatically. The flip: stop writing to docs/ideation/ and docs/plans/ entirely. CE outputs get distilled into the appropriate CLAUDE.md file — workspace-level decisions go into /Athian/CLAUDE.md, repo-level patterns into the per-repo CLAUDE.md, cross-repo decisions into the workspace layer with explicit @import directives. Discoverability comes from the context hierarchy, not from a directory tree. The artifact is the context, not a record of what the context used to be.

Axis
CLAUDE.md hierarchy · discoverability · artifact lifecycle
Basis
direct: three-tier CLAUDE.md hierarchy "partially in place"; @-import for canonical shared.md noted in grounding. external: research on master reference documents (arXiv 2604.04258) shows single evolving doc raises AI quality — the CLAUDE.md already serves this role. reasoned: docs/ adds a second system that the first system (CLAUDE.md) already covers better.
Assumption broken
"AI context and planning artifacts are different things" — a decision that doesn't reach the AI context on the next session hasn't been documented, it's been archived.
Risk
CLAUDE.md bloat if every CE output gets distilled in. Needs a strict discipline: CLAUDE.md gets the decision, not the reasoning. Reasoning goes to Linear if it needs to be preserved at all.
Meeting test

"When's the last time you opened docs/solutions/ without being in a CE session?" — if the answer is "never," the directory exists for the AI, and the AI should just read its own files.

03
Assumption-breaking Constraint-flipping: session boundary

Sessions are stateless by design. The only persistence is the commit or the issue.

The assumption: session continuity requires saving the artifact. The flip: what if sessions are designed to be stateless, and the only thing that outlives a session is a git commit or a Linear issue? The done skill already writes a session log — but the log is itself another artifact to manage. Invert this: instead of the session log as the persistence layer, treat every CE session as ephemeral by design. The session produces exactly one durable output: either a commit (code changes, CLAUDE.md updates) or a Linear issue (decision recorded, work item created). No docs/, no handoff files, no session logs. The HANDOFF.md currently in /Athian/ is a symptom of this: it exists because sessions aren't designed to end cleanly, so there's residue to hand off.

Axis
session continuity · artifact lifecycle
Basis
direct: HANDOFF.md exists in /Athian/ — a real symptom of session residue that doesn't have a clean home. direct: done skill writes session log. reasoned: if the session log is the continuity mechanism, then every session requires reading the session log — which is a fixed cost that compounds. A Linear issue costs zero to read the next time you open the project.
Constraint flipped
Zero sessions to continue → no session boundary problem. Each session is a complete unit. If you need to continue, you open the Linear issue — which was always the right artifact.
What this costs
Exploratory sessions (ideation, brainstorming) don't always produce a commit or an issue. Needs a third option: "close without output, intentionally" — the session is the thinking, and that's allowed.
Meeting test

"What does a well-run CE session produce?" — if the answer isn't instantly obvious, the system is accumulating artifacts instead of decisions.

04
Assumption-breaking

Location is determined at commit time by frontmatter, not by where you ran the session.

The assumption: humans should decide where to commit artifacts. The flip: the artifact carries its own routing instructions in frontmatter, and the done skill reads those to determine where to commit, not where the session happened to start. A CE output with repos: [duita, sus-plat] and type: decision gets committed to the workspace CLAUDE.md automatically. An output with type: plan and milestone: Nestle POC creates a Linear issue and commits a plan file to the designated planning location. The session runner doesn't think about storage — they think about the artifact. This is the "humans shouldn't decide where to commit" constraint flipped: the system routes, the human authors.

Axis
artifact lifecycle · session continuity
Basis
direct: docs/solutions/ YAML frontmatter pattern already in use (module, tags, problem_type). direct: done skill already writes session log. reasoned: the frontmatter convention is already installed — extend it rather than add a new system. The routing logic is a small addition to the done skill or a post-hook.
Assumption broken
"Humans should decide where to commit artifacts" — the human already made this decision when they wrote the frontmatter. The commit is mechanical from there.
Implementation note
Requires: (1) frontmatter schema extended with type:, repos:, commit_to:. (2) done skill updated to read frontmatter and route. (3) a small Linear MCP call for type: issue outputs. All three are small — the n8n pipeline already validates this pattern.
Meeting test

"Should a planning artifact know where it belongs?" — yes, obviously. Everything else in software that knows where it belongs gets routed automatically. Artifacts shouldn't be different.

05
Assumption-breaking

The organizing unit is the person, not the repo. Planning lives in dotfiles.

The assumption: the repos are the right unit of organization for planning work. The flip: planning context is personal — it belongs to Dory, not to duita or sus-plat. The dotfiles repo (/Users/doryweiss/dotfiles/) is already in use (CLAUDE.md with voice spec). Add a work/ directory there: cross-repo planning context, active decisions, a personal ADR log. Each repo gets only the CLAUDE.md it needs via --add-dir. The workspace-level context (what Dory is working on, what decisions she's made across repos) lives with her, not with any repo. When she hands something off, she exports the relevant slice to Linear. The repos stay clean; the person carries the context.

storage location · CLAUDE.md hierarchy
Basis
direct: dotfiles repo at /Users/doryweiss/dotfiles/ with CORE_VOICE.md, VOICE_CHECKLIST.md, VOICE_EXAMPLES.md already structured. direct: Claude Code --add-dir flag and CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 available. reasoned: the HANDOFF.md in /Athian/ is personal working state that doesn't belong to any repo — it should live with the person.

06
Constraint-flipping: scale to 1

Design for 1 engineer. Grep is discovery. Everything else is premature infrastructure.

The constraint flip: if this were a team of 1, there would be no discoverability problem at all. The only person who needs to find an artifact is the person who made it — and they remember roughly when and why. grep -r "Nestle" /Users/doryweiss/Athian/docs/ is instant. A tagging system, a planning manifest, a cross-repo routing layer — all of these are solutions to a team-scale discoverability problem that doesn't yet exist at Athian's actual size. The right design for a team of 4 engineers (under 10) is: flat, readable, grep-able. The investment in a more elaborate system should be triggered by the first time grep fails, not anticipated in advance. This idea isn't "do nothing" — it's "the simplest thing that actually works at your current scale, deferred scaling infrastructure until scale forces it."

Axis
discoverability · storage location
Basis
direct: "Small team driving AI adoption culturally" — team under 10 engineers. reasoned: discoverability infrastructure (tagging, manifests, routing) produces compounding value only at team scale. At 1-4 engineers, grep + Linear + memory covers 95% of cases. external: YAGNI applied to organizational infrastructure, not just code.
Constraint flipped
Team of 1 → no discoverability system needed, ever. Team of 100 → complex routing and tagging essential. At ~4 engineers: the minimum viable system is a flat directory + grep + Linear for shared decisions. Period.
What this changes
The docs/ directory stays, but the frontmatter schema, the routing conventions, and the planning manifest get deferred. One decision: "cross-repo planning context lives in /Athian/ and is grep-able." That's the whole system.
Meeting test

"Has grep ever failed to find a CE artifact?" — if the answer is no, the discoverability system you're designing is solving a hypothetical problem. Ship the simplest thing; revisit when grep fails.

07
Constraint-flipping: category

Plans are tests. Abandoned plans fail CI. Nothing gets "forgotten."

The category flip: what if CE planning artifacts were treated as test fixtures rather than documents? A plan file at _plans/nestle-pilot.yaml carries structured frontmatter (repos, milestone, owner, status: active|closed|blocked). A lightweight CI check (a GitHub Action on the workspace repo, if it's git-initialized) validates that every active plan file is complete — has all required fields — and that no plan has been in status: active for more than N days without a commit referencing it. Plans don't get abandoned; they rot visibly. A plan that hasn't been touched in 30 days produces a CI warning: "Plan nestle-pilot.yaml has had no referenced commits in 30 days — close it or update it." This is accountability as infrastructure: the system notices when planning artifacts diverge from what's actually happening.

Axis
artifact lifecycle · discoverability
Basis
direct: docs/solutions/ YAML frontmatter already in use — machine-readable shape exists. direct: NO cross-repo relationship layer exists — plans currently have no lifecycle visibility. reasoned: the HANDOFF.md in /Athian/ contains next steps that have no enforcement mechanism; this treats that problem structurally rather than procedurally.
Constraint flipped
Category flip: plans are docs (soft, ignored, forgotten) → plans are tests (assertions, enforced, visible). The workspace repo (if git-initialized) gets a GitHub Action. Cost: one yaml file, one workflow.
Aesthetic risk
This is the sharpest idea here and the one most likely to be rejected as "too much." It is also the only one that makes planning artifacts structurally accountable rather than culturally expected. "We'll keep it updated" is not a system; CI is a system.
Meeting test

"How do you know when a plan is abandoned vs. just paused?" — if the answer is "we check manually" or "we don't really," this idea is the only one that closes that gap without depending on discipline.

True monorepo migration Subsumes the actual problem. Migrating platform + sus-plat + duita into one monorepo is a multi-month engineering project that answers a different question than "where do CE planning outputs live." Dropped as orthogonal and overscaled.
