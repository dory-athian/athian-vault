Topic Context

Problem Shape

CE outputs (ideation .html, plan .md, brainstorm .md, HANDOFF.md) land in docs/{ideation,plans,brainstorms}/ — outside git, untracked, unshared, undiscoverable. Nothing happens downstream. The working frame: CE value should materialize in Linear issues, CLAUDE.md entries, and Slack threads. The CE doc is scaffolding.

Stated Constraints

  • Tools: GitHub, Slack, Linear (Compliance), Jira (Sustainability), n8n (live), Figma
  • n8n Feedback Hub pipeline already debugged: Granola → n8n → Sheets → Claude
  • Linear MCP + CLAUDE.md both required for skills to route correctly — silent fallback otherwise
  • HANDOFF.md is manually written, single-threaded, no multi-user support
  • ~10 engineers; Dory is VP Eng + acting VP Product

Key Pain Points

  • 17+ .html files from one session, zero downstream actions (17:0 generate-to-act ratio)
  • HANDOFF.md is Dory's state, not team state — overwrites silently on concurrent use
  • Plans orphaned from the issues they should create
  • docs/ has no index and no search entry point
  • CE skills silently route to wrong tracker when MCP not configured

Broken Assumptions

  • "CE outputs need to be stored" → they need to be acted on; storage is incidental
  • "The session is the value; the file is the record" → the file is only valuable if it causes something
  • "Plans and ideation are different artifact types" → one artifact at different lifecycle stages
  • "Session continuity is a memory problem" → it's a retrieval problem

Idea 1 · Storage location

Git-track docs/ and use push as the lifecycle trigger

Storage location Conf: High Cx: Small

The single highest-leverage change: move docs/ into a git-tracked location (or initialize the Athian directory as a git repo). Every CE artifact immediately gets version history, diff, PR review, and — critically — GitHub webhook events. A GitHub Actions workflow on docs/plans/** push can parse frontmatter and create Linear issues automatically. This is the prerequisite that unlocks almost every other automation on this list: the CI/CD pattern applied to planning artifacts rather than code.

Basis · Rationale · Downsides
Basis
direct/Users/doryweiss/Athian is confirmed not a git repo — outputs are untracked. The Feedback Hub n8n workflow (direct precedent) already does file-event → structured extraction → downstream action. CI/CD pattern: push triggers pipeline.
Rationale
Git-tracking docs/ is a prerequisite for almost every other idea on this list. It costs one git init and one .gitignore configuration. After that, GitHub webhooks, diff, PR review, and GitHub Actions are all available. The downstream automation stack becomes available for zero additional infrastructure cost.
Downsides
Requires deciding what else lives in the Athian directory that shouldn't be committed (feedback_hub_schema.xlsx, projects/, etc.). A .gitignore configuration pass is needed first. Also: HTML ideation files are large blobs — consider LFS or committing only .md artifacts to git.

Idea 2 · Artifact lifecycle

Linear as the CE thread system of record

Artifact lifecycle Conf: High Cx: Medium

One Linear issue per CE thread (an ideation topic, a plan, an execution spike), serving as the spine. The issue description holds the goal; comments hold stage transitions (ideation → plan → executing); attachments link the CE artifacts; child issues are the downstream work items. Status field tracks the lifecycle: Open → Refining → Plan → Executing → Done. This makes every CE thread queryable, assignable, commentable, and linked to the work it spawned — none of which the local file system provides.

Basis · Rationale · Downsides
Basis
externalMindStudio 2026: issue trackers as agent infrastructure — tickets as state machines, comments as message bus, labels as metadata. Five capabilities agents need that issue trackers already provide: persistent state, ownership, permissions, structured history, webhook layer. Athian already has Linear MCP live for Compliance work.
Rationale
Linear already has everything a CE thread needs: a URL, an owner, a status lifecycle, comments, linked issues, webhook events, and search. Using it as the spine doesn't require building any new infrastructure — only a convention about how CE threads are created and labeled. The artifact lifecycle problem is solved by the issue tracker's existing data model.
Downsides
Requires a naming/label convention the team adopts and maintains. If CE threads mix with regular issues, the signal-to-noise ratio in Linear degrades. A dedicated CE label or project within Linear is needed. Also: Jira (Sustainability) vs Linear (Compliance) split means CE threads for different scopes land in different trackers.

Idea 3 · Session continuity

Replace HANDOFF.md with a Linear issue + session-start live query

Session continuity Conf: High Cx: Medium

Drop HANDOFF.md entirely. Instead, a CE session start triggers a live query to Linear: open CE threads for this repo, recent decisions in the last 7 days, active plans. Claude reconstructs its context from current issue state rather than a stale file. Session end updates the relevant Linear issue with new decisions and next steps — no separate file to write. The handoff is always current because it's pulled live, not stored. This solves the concurrent-user problem (HANDOFF.md overwrites silently), the staleness problem, and the "Dory's state vs team state" problem simultaneously.

Basis · Rationale · Downsides
Basis
reasonedHANDOFF.md is a workaround for the absence of a shared, persistent, queryable session state store — it literally is a text file encoding what an issue tracker already provides. Session continuity is a retrieval problem: at session start, Claude needs to know what was decided and what's pending. That information exists in Linear issues and git commits. A live query is always current; a file is always stale.
Rationale
Removes the end-of-session manual write step (the highest-friction point — it's when you're tired and most likely to skip it). The engineer starting fresh work gets a current-state summary without relying on the prior engineer to have done anything. The handoff exists when needed, reconstructed from current state.
Downsides
Requires Linear MCP to be available and correctly configured (both CLAUDE.md and MCP server must be present — known silent-failure risk documented in docs/solutions/). Also requires a convention for how CE threads are tagged in Linear so the query finds the right things. The query needs to be built into a skill or hook.

Idea 4 · Artifact lifecycle + Discoverability

n8n lifecycle pipeline — plan→issue decomposition + Slack digest

Artifact lifecycle Discoverability Conf: High Cx: Medium

Extend the Feedback Hub n8n pattern to CE artifacts: a file watcher (or GitHub Actions webhook after idea 1 is implemented) triggers on new files in docs/plans/. n8n parses the plan's YAML frontmatter and section headers, creates Linear issues for each section tagged as a work item, and posts a one-line summary to #engineering Slack with a link. Two outputs from one pipeline: discoverability via Slack notification, and artifact lifecycle closure via issue creation. The build is a weekend given the existing Feedback Hub workflow as direct precedent.

Basis · Rationale · Downsides
Basis
directFeedback Hub workflow QU1ak4vCs0KkoaEJ — live, fully debugged. Architecture is identical: trigger → parse structured content → create downstream record. n8n has native Linear nodes. 10 bugs documented and fixed across two sessions. The pattern is proven at Athian specifically.
Rationale
n8n is already the automation runtime at Athian and the team has debugged it extensively. Extending a working, documented workflow pattern has dramatically lower build risk than building from scratch. The Feedback Hub's bug archive is effectively documentation for pitfalls to avoid in this build.
Downsides
Requires YAML frontmatter on plan files (idea 6 is the prerequisite). Also requires deciding the trigger mechanism: file watcher in n8n (polling-based, slight latency) vs GitHub Actions webhook (requires idea 1 — git-tracking — to be done first). The Slack notification is only useful if the team actually watches #engineering.

Idea 5 · CLAUDE.md / context hierarchy

CLAUDE.md as living decisions index, auto-updated from CE outputs

CLAUDE.md / context hierarchy Conf: High Cx: Small

A section of CLAUDE.md (the dotfiles symlink target, not the repo CLAUDE.md) maintains a running index of active CE decisions — one line per decision, pointing to its Linear issue or plan file. The /ce-compound skill already writes to docs/solutions/ after CE sessions; extend this to also append decision entries to a ## Active CE Decisions section in CLAUDE.md. Future sessions inherit these decisions without re-reading source artifacts. Context compounds: each session builds on prior decisions rather than starting from scratch. This is the session-continuity mechanism that doesn't require Linear to be configured.

Basis · Rationale · Downsides
Basis
direct/ce-compound skill already writes to docs/solutions/ with YAML frontmatter — same pattern, different target. Multi-repo CLAUDE.md hierarchy (external: karun.me, 2026): org > team > repo layers; one-line descriptions prevent drift. The CLAUDE.md at Athian is a symlink to /Users/doryweiss/dotfiles/CLAUDE-work.md — editing the real file rather than the symlink is the known-solution pattern.
Rationale
CLAUDE.md is loaded at every session start — it's the highest-leverage location for context that needs to be available without retrieval. Decisions written there are free at session start; decisions in Linear require an MCP query. This is the fallback continuity mechanism that works even when Linear isn't configured correctly.
Downsides
CLAUDE.md grows without pruning, and stale decisions are invisible (there's no "this was superseded by" mechanism unless one is built). The symlink issue means the write target must be resolved at automation time. Also: this is AI context, not human context — team members don't benefit from CLAUDE.md entries the way they benefit from Linear issues.

Idea 6 · Discoverability

CE artifact YAML frontmatter + automated CE-INDEX.md

Discoverability Conf: High Cx: Small

Add YAML frontmatter to every CE artifact with fields: status, linear_issue, jira_ticket, axes, session_id, created. A post-write hook (or the CE skill itself) maintains a docs/CE-INDEX.md — one line per artifact, organized by subject area and date. The index is the discoverability surface; the artifacts are the source. The session ID field links all artifacts from a single session, making the full session trace queryable. This is the minimum viable discoverability solution: no infrastructure, human-readable, greppable, and an entry point for any future search automation.

Basis · Rationale · Downsides
Basis
directdocs/solutions/ already uses YAML frontmatter with module, tags, problem_type — the learnings-researcher agent searches by it. The pattern is proven and the tooling (grep-based search) is already in place. Extending frontmatter to ideation/plans/brainstorms is a direct convention extension, not a new pattern.
Rationale
Once all CE artifacts have structured frontmatter, every existing search tool (grep, the learnings researcher, future automation) can query them. The session ID field is the key that enables "show me everything from the session where we planned the compliance pilot" — a query that's currently impossible. CE-INDEX.md is the human-readable entry point that requires no new tooling at all.
Downsides
HTML ideation files can't have YAML frontmatter in the traditional sense — the frontmatter would need to be in an HTML comment or a visible header section. Plan and brainstorm .md files can use standard frontmatter. CE-INDEX.md requires either a post-write hook or manual maintenance — the value degrades immediately if maintenance is skipped.

Idea 7 · Storage location

Skip local files entirely — write to Linear first

Storage location Conf: Medium Cx: Medium

The most radical inversion: CE skills write a Linear issue as the primary artifact. No local file is created. The issue description holds the plan; comments hold decisions and next steps; attachments hold any rendered CE output if needed. The local HTML/MD can be generated on demand from the Linear issue. This eliminates file management, the git-tracking question, the discoverability problem, and the docs/ maintenance problem in one move. The constraint is that it requires the Linear MCP to be reliably available and correctly configured — the known silent-failure risk must be solved first.

Basis · Rationale · Downsides
Basis
reasonedBreaking the assumption: "CE outputs need to be stored somewhere." Issue trackers already have the five capabilities needed (persistent state, ownership, permissions, history, webhooks). Linear's search is better than find docs/ideation/ -name '*.html'. The local file is a rendering artifact, not the source of truth.
Rationale
This is the cleanest expression of the zero-state/transience frame. If it works, it's the simplest possible architecture. Zero file management, zero git-tracking complexity, zero discoverability infrastructure. Linear's existing capabilities (search, assignment, linking, webhooks) replace every custom solution needed for the file-based approach.
Downsides
High dependency on Linear MCP reliability — the known silent-fallback failure mode is a blocker here, not just a nuisance. CE skills need to be modified to write to Linear rather than local files, which is a more significant change than any other idea on this list. HTML rendering is Linear-native only (limited formatting vs a full HTML artifact). Rated medium confidence because the MCP dependency risk is real.
