Idea 1 · Survivor

The Three-Horizon Compliance Record

Axis: Supplier experience + Standard lifecycle Confidence: 88% Complexity: High
Description

A supplier's compliance state in the DSL-first architecture is not a score or a PDF — it is a continuously-evaluated, timestamped evidence plan that exists across three time horizons simultaneously. In the past horizon, every evaluation is appended to a cryptographically-ordered history: a supplier who has maintained passing methane intensity for 18 consecutive months holds a materially stronger record than one who passed last quarter, and any new buyer can inspect that record on enrollment rather than commissioning an audit. In the present horizon, when Athian's incentive layer records an intervention event — a producer adopting Bovaer, completing an AMMP cycle, adding monitoring infrastructure — the DSL plan auto-re-evaluates every requirement that cites the intervention as accepted evidence, and the updated compliance state propagates to every buyer whose profile references that requirement. The supplier does not re-document; the system re-runs the function. In the future horizon, because DSL requirements are executable functions (typed inputs → deterministic output), the system can run a forward simulation before any evidence is collected: given a proposed intervention + a time period, what would compliance state be? A CPG can model "if we enroll this supplier in Bovaer for Q3, they will satisfy our methane intensity requirement by Q4" before committing program budget — and the supplier can see exactly which interventions would move them to full compliance with any buyer's profile.

The unit of portability is the evidence plan itself — not a summary score, not a document. Each requirement evaluation is a tradeline: typed requirement, current result, supporting evidence, timestamp. New buyers see both the summary state and the tradeline detail. Existing buyers receive propagated updates when evidence changes. The supplier controls the record and earns commercial leverage from its history: faster enrollment, better terms, program priority from CPG buyers who can see a long clean record rather than commissioning a fresh audit.

reasoned: The credit bureau analogy in the brief names the right structure but understates the DSL advantage. A credit bureau issues a score derived from tradelines — but the tradelines are not directly portable; lenders see a derived summary. In the DSL-first architecture, the tradelines (requirement evaluations) are the portable unit, and the score is derived from them. This means any buyer can inspect the basis of the score, not just consume the verdict. EcoVadis cannot do this: its score methodology is opaque and the evidence is not buyer-inspectable. The DSL record is more analogous to an open-tradeline credit report than to a credit score — the difference matters for high-stakes procurement decisions where buyers need to know not just the result but whether the evidence supports it.
reasoned: The simulation capability (future horizon) is structurally impossible in document-based systems. A PDF audit has no function signature — it cannot be re-run with projected inputs. A DSL requirement has an explicit type signature (evidence_type, value, threshold, time_period → pass/fail/partial). Re-running it with projected inputs is the same computation as evaluating it with real inputs. This means compliance planning ("what interventions would get this supplier to compliance?") is a first-class feature of the architecture, not a separate modeling exercise. Suppliers gain a navigation tool — they can see exactly which interventions close the gap with any buyer's profile.
Why It Matters

This changes the product in two ways that compound. First, the supplier finally has a commercial reason to invest in the compliance record: a three-horizon history is a durable, portable asset that follows them across buyer relationships, accelerates enrollment with new buyers, and — via the simulation capability — tells them precisely which interventions are worth making. The record is theirs. Second, the standard lifecycle is no longer a buyer-side workflow. When a protocol updates its threshold (Bovaer baseline, AMMP measurement methodology), the catalog change triggers automatic re-evaluation for every affected supplier plan. No buyer needs to re-initiate an audit; no supplier needs to re-document. The standard's version propagates through the system as a computation event. This is the mechanism EcoVadis structurally cannot offer — its assessment cycle is annual and buyer-triggered by design.

For the market: if this works, Athian owns the compliance infrastructure layer for livestock/ag Scope 3, not just a point-solution for individual CPG programs. The network effect is real: each additional buyer who enrolls expands the value of each supplier's history record, and each additional supplier who builds a long record makes Athian's platform a more credible source of truth than any single-buyer audit.

Downsides and Costs
  • Supplier consent architecture is non-trivial. The supplier must consent to sharing their record with each buyer, and consent granularity matters — a supplier may want to share history with Buyer A but not Buyer B. This is a product design and legal challenge, not just a technical one.
  • DSL requirement versioning is load-bearing and hard to get right. When a protocol updates, which version of the requirement does each buyer's profile reference? If Buyer A is on v1 and Buyer B is on v2, the supplier's record must evaluate against both. Requirement version management is a first-class engineering problem.
  • Simulation accuracy depends on evidence model completeness. If the DSL requirement cites an evidence type that doesn't have a clean parametric model (e.g., practice adoption that requires on-site verification), the simulation degrades to a rough indicator rather than a defensible projection.
  • History length creates a cold-start problem for new suppliers. The history asset takes time to build. New suppliers entering the system have no record advantage — Athian would need an onboarding path that bootstraps history from prior program participation where verifiable.
  • Complexity is high. This is not a feature on top of the existing architecture — it is the architecture. Building it requires that the DSL evaluation engine, the event propagation layer, and the consent/sharing model all work correctly before the value of the history record becomes visible to suppliers or buyers.
Meeting Test
What a strong CPG product team says when they hear this "Our compliance team spends weeks re-auditing suppliers who were clean with another buyer six months ago — if their record is already here and current, we could cut enrollment time by 80% and reallocate that spend to suppliers who actually need it."
