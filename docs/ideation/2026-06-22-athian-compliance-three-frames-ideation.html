Grounding Context

Topic Context

Platform
Athian Compliance — AI-native, DSL-first compliance platform. Compliance requirements are machine-readable: typed with unit, threshold, time window, required data, and accepted sources.
Structural problem
One evaluator assessing many suppliers against a shared spec. Evidence arrives heterogeneous (PDFs, certificates, lab results, audit reports). The spec changes over time and must be re-applied to existing entities.
Key assumptions broken
Push model (suppliers submit). Specialist reviews each supplier. Standards defined externally. Compliance assessed periodically. Suppliers are passive actors.
External anchors
NIST OSCAL, SBOM/EO 14028, Vanta/Drata, EcoVadis, SOC 2 continuous monitoring, W3C Verifiable Credentials 2.0, Aviation ADs, Nuclear reactor tech specs, CSDDD/EU DPP 2026–2030.

1
Assumption-breaking Standard encoding

Compliance Specialist as Author, AI as Assessor

ConfHigh
CxMedium

The current design puts the compliance specialist downstream: they receive AI pre-assessments and review them. Invert the division of labor — the specialist authors requirements directly in a structured DSL interface (unit picker, threshold input, time window, accepted source multi-select), and the AI takes over all assessment work from that moment forward. The specialist's expertise is in what compliance means; the AI's capability is in evaluating evidence against specified criteria. Today's design wastes one while under-using the other.

Illustrative — the division of labor before and after the assumption is broken

Basis
reasoned EcoVadis's limitation — fixed schema per standard, requiring vendor development to add a new standard — is a direct consequence of not having a specialist-facing authoring interface. The DSL already defines the type system; making it writable via a structured UI is the gap. The assumption that standards are "defined externally" is a choice, not a constraint.
Why it matters
Changes the product category from a compliance automation tool to a compliance standard platform. CPG customers don't just run externally-defined standards — they create proprietary supplier requirements. Authorship makes those requirements portable and machine-assessable from creation, without engineering work for each new standard.
Downsides
Requires a well-designed authoring UX — if the interface is hard to use, specialists won't author requirements correctly. Training investment needed. Risk of requirements authored inconsistently across compliance teams unless the DSL type system enforces structure.

How many CPG customers have requested custom requirement modifications, and how long does it currently take to implement them?

Cross-domain analogy Standard encoding

Package Manifest Model for Standard Composition

ConfHigh
CxHigh

A CPG company's compliance standard is a manifest that declares which requirement blocks are included, at what version, with which threshold parameters — the same way an npm package.json declares dependencies. Updates to an upstream requirement block cascade to all manifests that include it, with a semantic diff showing what changed. Suppliers respond to the resolved manifest, not a monolithic standard document. The lock file is the resolved compliance state.

Analogy domain
Software dependency management — npm, pip, Cargo
Why the analogy holds
reasoned Software packages and compliance requirements share the same fundamental structure: composability of versioned artifacts across a distributed network of consumers who need to track changes without re-specifying everything from scratch. NIST OSCAL intuited this with its catalog/profile/plan layers but stopped short of the full dependency resolution model — npm has semver ranges; OSCAL has no equivalent. That gap is the opportunity.
Why it matters
Standard composition via manifest would let a CPG company assemble a bespoke standard from upstream requirement blocks without encoding it from scratch. Automatic propagation of upstream changes eliminates the current manual diff process entirely. The shared library of requirement blocks becomes a compounding network asset — each new standard encoded makes the next one cheaper to build.
Downsides
Requires building a requirement block library first. Version conflict resolution is non-trivial when two manifests include different versions of the same block. Semver semantics for compliance thresholds need definition.

Would the team recognize the catalog/profile/plan architecture in NIST OSCAL as a proto-manifest system, and what would semver-style requirement versioning add?

3
Constraint-flipping Evidence collection

Zero-Submission Evidence Architecture

ConfHigh
CxHigh

The extreme constraint flip — "what if evidence was never submitted but always available?" — produces a three-tier evidence architecture. Tier 1: pulled directly from authoritative source systems (USDA Organic Integrity, ISO accreditation registries, third-party auditor portals) on a scheduled basis. Tier 2: supplier-configured standing authorizations to pull from their internal systems (ERP, LIMS, herd management software). Tier 3: requested submission for items not available in Tiers 1 or 2. Submission becomes the exception, not the rule.

Resolution order: Tier 1 first → Tier 2 → Tier 3 (submission). The DSL requirement's "accepted sources" field encodes which tier applies.

Basis
reasoned Aviation AD pull model is the Tier 1 operating pattern; Vanta/Drata's 400+ integrations is the Tier 2 model. The DSL requirement's "accepted sources" field becomes a resolution order — the system tries Tier 1 first, then Tier 2, then falls to Tier 3. SBOM showed that mandated ingestion without tooling support fails for smaller suppliers; the tiered model lets supplier capability determine which tier applies.
Why it matters
This is the architecture that makes 10,000 suppliers feasible. At that scale, manual submission management is impossible. Getting the tiered pull architecture right now positions for volume scaling and eliminates the most common failure mode (a compliant supplier forgets to submit).
Downsides
Significant integration engineering work for Tier 1 and Tier 2 source connectors. Supplier authorization flow for Tier 2 requires trust infrastructure. Some evidence types may have no automated source, keeping Tier 3 permanently in play.

What percentage of current evidence types have a Tier 1 or Tier 2 source that could be pulled rather than submitted?

4
Inversion / automation Supplier experience

Ambient Attestation — Email-Native Compliance for Zero-Tech Suppliers

ConfHigh
CxLow

For suppliers with zero technical capacity, any portal is too much. An ambient attestation model replaces the portal with a structured email digest: "Here's what we need from you this month — click to confirm each item still applies or attach a file." The interaction surface is email; the back-end writes a structured attestation to the DSL. Suppliers with technical capacity get the full portal; suppliers without get email-native compliance. The portal becomes one channel, not the only channel.

Basis
reasoned The constraint flip "what if suppliers had zero technical capacity?" produces this design. Large suppliers managing 15–30 portals experience re-entry friction. But the smallest suppliers in the livestock supply chain (individual ranchers, small feedlots) have no compliance staff at all. Ambient attestation meets them where they already are rather than requiring tool adoption.
Why it matters
If the platform's weakest link is small-supplier participation, reducing the entry floor from "navigate a portal" to "respond to an email" expands the addressable supply chain. It also shifts the compliance specialist's outreach from manual follow-up to exception-handling on non-responses.
Downsides
Email attestation provides weaker evidence than document submission. Self-attestation without verification creates a fraud surface. Needs a clear escalation path when email attestation is insufficient for a given requirement type.

What's the participation rate for the smallest-tier suppliers, and what's the primary dropout reason?

5
Constraint-flipping Supplier experience

Supplier-Authored Compliance Profile with AI Verification

ConfHigh
CxMedium

Invert the supplier's role from passive responder to active profile author. The supplier describes their own practices, certifications, and evidence in a structured self-attestation tool — "here's what we do, here's the evidence." The AI then maps that self-description against every active DSL standard in the system and identifies gaps. The specialist reviews AI's gap analysis, not a pile of supplier-submitted documents. Instead of the platform asking "do you have X?" — the supplier says "here's what I have" and the AI figures out how it maps.

Basis
reasoned The constraint flip "what if suppliers authored their own compliance profile?" surfaces the self-attestation-plus-AI-mapping design. Suppliers already know what they have; they don't know what standard it maps to. This reverses the information flow. The compliance specialist's review becomes a verification of the AI's mapping, not an extraction of facts from supplier submissions — the same shift that makes code review faster than code writing.
Why it matters
Self-attestation with AI verification scales differently. Suppliers are motivated to be thorough; the AI handles the mapping; the specialist validates mapping quality rather than completeness of submission. For large suppliers with complex multi-standard footprints, this eliminates back-and-forth cycles dramatically.
Downsides
Supplier self-attestation may be over-optimistic or strategically incomplete. The AI's mapping accuracy is critical — a missed mapping is a gap the specialist may not catch. Requires high AI recall on the mapping step.

What percentage of requirements could the AI assess without specialist review in a self-attestation model?

Cross-domain analogy Supplier experience

DSL as Exportable Compliance Passport

ConfHigh
CxMedium

Once a supplier's evidence is indexed against a typed DSL, that compliance state is portable. Issue a signed compliance passport — a W3C Verifiable Credential — that the supplier can present to any other CPG customer or standard body without re-submitting evidence. The passport is cryptographically tied to the DSL requirements it satisfies and the evidence that backs it. Every supplier who adopts the platform becomes a distribution channel: "We have an Athian compliance passport — can your system accept it?"

Basis
external W3C Verifiable Credentials 2.0 (2025) provides exactly the cryptographic infrastructure for this. SBOM mandates showed that once a portable format exists, adoption compounds — the format becomes a prerequisite for doing business. EcoVadis's network effect comes from buyers demanding the EcoVadis score; the same dynamic applies here with a technically superior (machine-readable, verifiable) credential.
Why it matters
Converts supplier adoption from a cost center (they participate because required to) to a supplier value proposition (their passport has value across multiple CPG relationships). Creates a compounding network: each passport issued makes the next CPG customer's procurement more efficient, which increases platform demand.
Downsides
Network effects require critical mass before the passport has value. CPG customers need to accept the credential format — requires business development, not just engineering. The trust infrastructure for credential revocation and expiration needs careful design.

Is the current platform single-CPG-customer per supplier, or can a supplier's evidence portfolio be shared across multiple CPG customers?

Constraint-flipping Review and reporting

Threshold-as-Trip-Wire — Trigger-Based Compliance Alerts

ConfHigh
CxMedium

The DSL's typed thresholds are not just assessment criteria — they're trip wires. When evidence is updated (via pull or push), the system evaluates it immediately against each threshold and emits a compliance event: PASS, FAIL, WARN (approaching threshold), or EXPIRED. No review cycle required — the specialist receives alerts only when a threshold trips, not on a calendar schedule. The "audit" becomes an exception-handling workflow. The constraint flipped: "what if the DSL defined compliance thresholds that triggered automatic alerts, not periodic reviews?"

Basis
external Nuclear reactor tech specs operate exactly this way — operating limits define automatic state changes (including shutdown triggers) that fire when readings cross thresholds, not when someone schedules a review. SOC 2 continuous monitoring achieved 30%+ audit cost reduction by replacing periodic review with continuous threshold monitoring. The DSL already has all the typed threshold information needed; the only gap is replacing batch assessment with trigger evaluation.
Why it matters
Periodic review cycles are an artifact of paper-based compliance. When evidence is digital and continuously available, real-time threshold evaluation is both cheaper and more accurate. The specialist's workload shifts from calendar-driven to exception-driven — which scales with compliance quality rather than with supplier count.
Downsides
Alert volume may be high without good calibration — every threshold crossing generates a notification. WARN threshold definition requires careful tuning to avoid alert fatigue. Regulatory context may still require periodic formal reviews even when continuous state is maintained.

What would the alert volume look like if threshold-based alerts replaced the review cycle for the top 20% of quantitative requirements?

8
Inversion / automation Review and reporting

Qualitative Review Rubric Engine

ConfHigh
CxMedium

Qualitative (process-based) requirements are the hardest review bottleneck — the AI assesses quantitative thresholds but defers all process evidence to the specialist. A rubric engine encodes qualitative assessment criteria as structured questions derived from each process requirement in the DSL: "Does the audit report confirm a documented HACCP plan? Does it include corrective action records from the past 12 months?" The AI answers each rubric question against the evidence; the specialist reviews the AI's rubric answers, not raw documents.

Basis
reasoned A compliance specialist reviewing a third-party audit report for a process requirement is running a mental checklist against the document. Making that checklist explicit as a DSL-derived rubric converts the specialist's role from extractor to verifier of AI-extracted answers — the same shift that makes code review faster than code writing. The bottleneck is not judgment; it's structured extraction from unstructured documents.
Why it matters
Qualitative requirements are often the ones that matter most for sustainability outcomes and the hardest to scale. A rubric engine that handles extraction leaves the specialist free for genuine judgment calls — which are the cases where their expertise is irreplaceable, not extractable.
Downsides
Rubric quality determines everything — poorly authored rubrics produce false positives. Rubric authoring requires the compliance specialist's time upfront. Some qualitative requirements may resist rubric decomposition (judgment-heavy, context-dependent assessments).

What percentage of specialist review time currently goes to qualitative vs quantitative requirements?

Cross-domain analogy Review and reporting

Epidemiological Surveillance Model for Compliance Risk

ConfMed
CxHigh

Epidemiological surveillance monitors populations for early signals of emerging risk — not waiting for confirmed cases but tracking indicators that predict outbreaks before they arrive. Apply this to supply chain compliance: instead of reviewing individual supplier files, monitor the portfolio for leading indicators of systemic risk — clusters of near-threshold performance, seasonal patterns in evidence expiration, supplier segments with declining trend lines. The specialist becomes an epidemiologist of the supply chain, not an auditor of individual files.

Analogy domain
Epidemiology — sentinel surveillance networks, R₀ threshold escalation
Why the analogy holds
reasoned Both domains face the same problem: a single monitoring function tracking distributed actors for early signals of a failure mode that's expensive to remediate once visible. Epidemiology solved this with sentinel surveillance (track a representative sample continuously) and threshold-triggered escalation (R₀ above 1.0 → outbreak response). The DSL's continuous threshold monitoring is already sentinel surveillance infrastructure; the missing piece is population-level signal aggregation.
Why it matters
A CPG company's real question is not "is Supplier X compliant?" — it's "where is my supply chain most likely to fail in the next 90 days?" Answering that question puts Athian upstream of the decision-making that actually matters to the CPG customer's procurement and risk functions.
Downsides
Requires meaningful historical data to establish baselines before risk signals are meaningful. Portfolio-level analytics are harder to explain to suppliers than individual compliance verdicts. False positives in risk signals could damage supplier relationships.

Does the platform currently produce any portfolio-level risk signal, or only individual supplier compliance verdicts?

Constraint-flipping Standard lifecycle

Weekly Standard Versioning — Standard as Continuous Spec

ConfMed
CxHigh

The constraint flip "what if the standard changed every week?" produces a continuous delivery model for compliance standards. Requirements are versioned individually, not monolithically; each has a pending update queue. Updates batch weekly with a grace period calendar: "Requirement 4c updates to v2.3 on [date] — here are affected suppliers and their grace periods." The specialist becomes a requirements product manager shipping standard updates on a cadence rather than rare high-stakes releases. The assumption that standards change rarely is a historical artifact of the manual update process, not an intrinsic property of compliance requirements.

Basis
reasoned Science-based sustainability thresholds (GHG intensity, feed additive efficacy, antibiotic use) update as research advances. When the DSL represents requirements as individually versioned artifacts (like software packages), governance can shift from infrequent monolithic releases to continuous small updates — the same shift DevOps applied to software deployment. W3C Verifiable Credentials already supports versioned credential schemas.
Why it matters
Standards that can only update infrequently fall behind the science. A platform enabling continuous small updates keeps the standard current with the best available evidence — which is the core scientific legitimacy claim for Scope 3 reduction programs. It also positions the compliance specialist as a standard maintainer, not just a reviewer.
Downsides
Supplier burden increases if updates arrive too frequently without adequate grace periods. Requires robust change management and communication tooling. May conflict with regulatory standards that specify fixed update cycles. Needs strong version rollback capability.

Are there requirements in the current DSL that the science team knows are outdated but can't update because the update process is too heavyweight?
