Grounding Context

Organization

Athian, growth-stage ag tech. VP of Engineering + ~10 engineers. Active AI adoption initiative — this infrastructure decision is a cultural demonstration, not just a tooling choice.

Repos

  • platform — monorepo backend
  • sus-plat — main frontend
  • duita — separate repo

Parent /Athian/ dir is NOT a git repo. Existing convention: docs/solutions/ per-repo with YAML frontmatter.

Tools in play

  • GitHub (Athian-ai org)
  • Claude Code
  • Linear (Compliance), Asana
  • n8n (automation)
  • Granola, Figma

Already evaluated (ruled out)

  • Meta-Repo / Repo-of-Repos
  • Spine Pattern (CLAUDE.md hierarchy + _tasks/)
  • Planning Repo (parent git ignoring nested)
  • Virtual Monorepo (.repos manifest)

External research

  • Context Engineering (arXiv 2604.04258): formalization dramatically improves first-pass AI quality
  • Production Bible (film): stable constitutional layer vs. operational scripts — collapsing both makes both worse
  • Multi-jurisdictional coordination (ICS/urban): explicit scope declarations are what make multi-authority coordination work
  • Lab notebooks: immutability of the record is the value — software docs overwrite it away
  • Freight manifest + event log: what's supposed to be true vs. what actually happened must be separate files

Key synthesis insight

"The real problem isn't storage — it's identity. A CE planning doc that touches two repos has no single 'owner' repo, which means any single-repo placement is a naming convention, not a fact. The tension between low-maintenance and high-discoverability is the actual design constraint, and it doesn't have a clean resolution — just tradeoffs to rank."

1

The Planning Ledger (MANIFEST + LEDGER)

Storage location High confidence Medium complexity

A dedicated athian-decisions repository stores exactly two files: MANIFEST.yaml — the current authoritative state of all cross-repo decisions, edited deliberately with PR review — and LEDGER.log — a timestamped append-only record of every planning session, decision, and reversal, never edited, only appended. PRs in all other repos reference a LEDGER entry ID. The manifest is what's supposed to be true. The ledger is what actually happened. They are never the same file.

Directional sketch — MANIFEST.yaml is the plan; LEDGER.log is the record. PRs reference LEDGER entries; Claude Code reads MANIFEST at session start.

Basis externalFreight logistics manifest + event log pattern — what's supposed to be true vs. what actually happened must be separate artifacts. The grounding research names this split explicitly as the most directly applicable external finding.
Why it matters Resolves the identity problem by refusing to solve it: no single repo "owns" a cross-repo decision — the ledger records it happened, the manifest declares what's currently true. At 10 engineers the split is lightweight; at 100 it's the only architecture that scales without losing history.
Downsides Requires maintaining a new dedicated repo. MANIFEST and LEDGER can drift — knowing when the MANIFEST is stale relative to the LEDGER needs a check. Some overhead to establish the PR reference convention across existing repos.
"So the MANIFEST and LEDGER would diverge by design — how do we know when a MANIFEST entry is stale relative to the LEDGER?"
2

The Inverse PR: Decision First, Code Second

Artifact lifecycle High confidence Medium complexity

Engineers open a Decision Record (DR) in athian-decisions before writing code. The DR gets a stable ID (DR-0047). Pull requests in platform or sus-plat include dr: DR-0047 in their description. A GitHub Action validates that the DR exists and is in an approved state before the PR can merge. Code is the implementation of a decision. The decision is the primary artifact.

Basis reasonedThe Production Bible pattern (film) separates constitutional layer from operational scripts. Current engineering practice does this backwards — PRs describe what code does; decisions are inferred after the fact. Inverting the dependency makes planning the gate, not the artifact that gets written if time permits.
Why it matters Gives CE artifacts actual enforcement leverage in the deployment pipeline rather than advisory status. For Athian's AI adoption initiative: Claude-assisted DRs gate code that skipped planning — the AI has visible teeth. Engineers feel the structure rather than having it suggested to them.
Downsides Most likely failure mode: engineers route around it on hotfixes or "quick" changes, which then become habit. Requires careful scoping of when a DR is required vs. optional to prevent friction from outweighing benefit. Needs a lightweight DR format to stay viable under deadline pressure.
"If we required a DR before any cross-repo PR, how long before the first engineer routes around it — and does that tell us the rule is wrong, or just that adoption takes work?"

Split the Constitutional Layer from the Operational Layer

CLAUDE.md / context hierarchy High confidence Low complexity

Athian maintains one CONSTITUTION.md per org — stored in a shared repo, referenced via @path include in each repo's CLAUDE.md — that holds stable architectural commitments, team conventions, and design system decisions. Daily CE outputs (plans, sessions, decisions) live in per-repo ce/ directories and never touch the constitutional layer. Constitutional changes require explicit team review; operational CE outputs do not. CLAUDE.md hierarchies currently collapse two different change rates into one file, making both worse.

Directional sketch — two change rates, two files. CLAUDE.md composes from both; each layer is authored and reviewed at its own cadence.

Basis externalFilm Production Bible pattern — constitutional (world-building rules, rarely touched) vs. operational scripts (daily work). Confirmed by Context Engineering paper finding that formalized, structured context improves first-pass AI quality.
Why it matters Engineers who want Athian's non-negotiable architecture decisions shouldn't have to filter through last Tuesday's session notes. Claude Code sessions reading only constitutional context get cleaner first-pass outputs on stable design questions. The split also makes architectural drift visible: any operational artifact that contradicts the constitution is a named conflict, not invisible.
Downsides Someone must maintain CONSTITUTION.md and make judgment calls about what's constitutional vs. operational — the line isn't always obvious. Teams tend to over-promote things to constitutional status early, inflating what was meant to be stable.
"What's the difference between a constitutional decision and an operational one — can we name three examples of each for Athian right now?"

Repos Are the Wrong Unit — Own the Intervention, Not the File

Storage location Discoverability High confidence Low complexity

CE planning doesn't belong to a repo; it belongs to an intervention — the cross-cutting change that happens to touch multiple repos. Instead of routing artifacts by repo, Athian routes them by Linear issue ID, which becomes the canonical home. Each repo gets a thin ce/ pointer file ("see ATH-1234") — no content duplication, no ownership ambiguity. Finding a CE artifact means searching Linear, not the filesystem.

Basis directThe synthesis insight identifies that "a CE doc that touches two repos has no single 'owner' repo — any single-repo placement is a naming convention, not a fact." Linear is already Athian's system of record for Compliance work; extending that identity to CE artifacts reuses existing muscle memory rather than introducing a new convention.
Why it matters Dissolves the placement debate entirely. "Where does this live?" has a non-arbitrary answer: wherever the work lives. Pointer files in each repo satisfy the "CE artifacts must live in a repo" constraint without requiring content duplication. Discoverability comes from Linear search, not a file convention everyone has to remember and maintain.
Downsides Depends on Linear's availability and search quality. If a CE artifact needs to be read by Claude Code during a session, fetching it from Linear requires an MCP call rather than a local file read — pointer files alone don't give Claude Code the content, only a reference.
"Should we stop filing CE outputs in repos at all and make Linear the canonical home, with pointer files in each repo satisfying the git-residence requirement?"

Dead-Letter Context: The Failure Archive

Session continuity Medium confidence Low complexity

Every ruled-out approach, abandoned plan, and superseded decision gets committed to a docs/dead-letters/ directory in athian-decisions with mandatory frontmatter: killed_by: DR-0031, reason:, date:. Claude Code, when beginning a new planning session, reads the dead-letter archive to avoid proposing approaches the team has already ruled out. The negative space is the context.

Basis reasonedThe grounding itself lists four evaluated-and-rejected patterns (meta-repo, spine, planning repo, virtual monorepo) that currently live only in the memory of whoever was in the room. If those rejections had been committed as dead letters, the next session would start with them as context. A system that only records what's true now loses the most valuable planning signal: what was tried and why it failed.
Why it matters At Athian's stage, institutional memory is thin. Dead letters make the negative space permanent and retrievable — for Claude Code and for humans. This is the cultural demonstration the AI adoption initiative needs: the system knows what the team already tried, session boundaries don't erase it, and new engineers don't re-propose rejected approaches.
Downsides Risk of becoming a graveyard nobody reads. Value depends on Claude Code surfacing dead letters at the right moment — not dumping them wholesale into context. Requires discipline to write dead letters at decision time rather than retroactively.
"What stops dead letters from becoming a graveyard — how does Claude know when to surface them versus when they're noise?"

Scope Declarations as First-Class Artifacts

Session continuity Medium confidence Low complexity

Before any cross-repo CE session begins, a ce/scope.md is committed that explicitly declares which repos are in scope, what decisions require cross-repo sign-off vs. local discretion, and who the session coordinator is. The scope declaration is the artifact that makes cross-repo work tractable. Sessions without a scope declaration are by convention single-repo and require no coordination.

Basis externalMulti-jurisdictional coordination research (ICS, urban planning) — explicit scope declarations are what make multi-authority coordination work. Software planning rarely does this, defaulting to informal designations that only the people in the room understand.
Why it matters Makes cross-repo work formally tractable instead of informally understood. A new session reads ce/scope.md and knows immediately what's in scope — solving the cold-start problem concretely. Claude Code can read the scope declaration and decline to modify out-of-scope files, enforcing architecture boundaries without a human gatekeeper.
Downsides Adds ceremony to every cross-repo session — easy to skip under deadline pressure. "Committing a scope declaration first" needs a lightweight enough format to stay viable in fast-moving contexts.
"Should starting a cross-repo feature require committing a scope declaration first — and what's the minimum it needs to say to be genuinely useful?"
7

TTL-Tagged Decision Records

Artifact lifecycle Medium confidence Low complexity

Every CE output gets a frontmatter field: expires: 90d. An n8n workflow (which Athian already runs) scans all repos nightly, flags expired artifacts as issues in Linear, and moves them to docs/solutions/archived/. Active planning docs are, by definition, recent. Stale architecture decisions are surfaced as tech debt rather than silently rotting.

Basis directAthian's existing n8n + Linear toolchain is real and operational — this is a new workflow built from existing infrastructure, not new tool adoption. externalFreight manifest/event log split: the manifest (what's currently true) must be actively maintained; expiry enforces that discipline rather than relying on hope.
Why it matters Athian's docs/solutions/ files have no lifecycle. A solution documented during Series A will sit there through Series B looking authoritative. Forced expiry makes the team either recommit to a decision or acknowledge it's no longer load-bearing. The infrastructure that survives expiry — the n8n workflow and the archive path — is the institutional memory.
Downsides Expiry timing is arbitrary and will generate noise. Some decisions should never expire (architectural foundations); others expire immediately. Requires triage discipline around the Linear issues generated — without it, the workflow becomes a noise machine.
"If a CE artifact expires, does that mean the decision expired, or just our documentation of it? Those are different problems with different solutions."

Engineers Aren't the Authors — CE Artifacts Are Co-Committed with Claude

Artifact lifecycle Medium confidence Low complexity

Claude is the primary author of all CE planning artifacts; the engineer is reviewer and committer. The artifact isn't done until Claude produces it and the engineer explicitly signs off — a PR approval or a co-author commit tag. Commit messages name Claude as co-author. This inverts the cultural dynamic: CE artifacts are evidence of AI-human collaboration, not human work with AI assistance.

Basis directAthian's active AI adoption initiative explicitly prioritizes cultural demonstration over mandates. The VP has stated cultural weight is the primary metric. A workflow where Claude's authorship is visible in the commit history is a daily proof-of-concept that AI-first engineering is real, not aspirational.
Why it matters Reframes CE artifacts from "documentation overhead" to "the artifact Claude and I made together." For a team still deciding whether AI tools are worth the friction, that reframe matters more than the storage location. The commit history becomes the proof that the team is working AI-first — visible to anyone who runs git log.
Downsides Co-authorship attribution is a tactic, not a guarantee of quality or adoption. An engineer who finds the workflow awkward will revert to writing the doc themselves and crediting Claude nominally. The cultural demonstration requires authentic workflow integration, not just a commit message format.
"What if every CE planning doc listed Claude as co-author — would that change how the team thinks about the process, or would it just be a convention we ignore after a week?"

Rejection Summary

#IdeaReason Rejected
A3 Artifacts Are Append-Only — Never Overwrite Near-duplicate of Idea 1 (Planning Ledger); the Ledger does append-only better via the explicit MANIFEST/LEDGER structural split. Append-only without the split accumulates contradictions that degrade AI context quality — basis doesn't engage with that failure mode.
A4 CLAUDE.md Is a Generated Artifact, Not a Source of Truth Refuted — basis inverts the arXiv paper's actual finding. The paper supports generating well-structured CLAUDE.md files; it doesn't support demoting CLAUDE.md to derived artifact status. YAML fragments being machine-parseable assumes a parser that doesn't exist at Athian.
A5 Discoverability Is a Pull Signal, Not a Search Convention Push-based systems require maintenance discipline the basis doesn't earn. "Athian uses Slack" establishes a vacuum, not a reason push-based discovery has lower adoption barriers. No dedicated process owner on a 10-person team to sustain it.
A7 The Repo Boundary Is an Accident — Own the Graph Instead Borrows monorepo benefits without acknowledging the mechanism that delivers them. Implementation gap is too large for a 10-person team without tooling that doesn't exist yet. Better explored as a brainstorm-level direction than an actionable idea now.
C1 The Context Injection API (manifest repo + CLI) Introduces the same synchronization problem it purports to solve. A manifest repo + CLI is a cache with a different invalidation failure mode, not a solution to cache invalidity.
C2 Git Notes as the Context Layer Git notes are not reliably propagated across clones and remotes — most hosting providers don't fetch them by default. This transport failure mode is disqualifying for a small team with no dedicated infrastructure ownership.
C4 Session Receipts, Not Documents Near-duplicate of A3 and Idea 1 (Planning Ledger). "Session receipt" framing is a label, not a structural distinction. What differentiates C4 from the Ledger is only granularity, which the Ledger handles better.
C5 Scope Declarations with Sign-Off Quorum ICS sign-off quorum exists because lives are at stake and authority is legally distributed — the mechanism doesn't fit Athian's actual barrier (speed and AI adoption). After the quorum mechanism is removed, what remains is Idea 6 (Scope Declarations), which survives on its own merits.
