Grounding Context

product

DSL-first compliance platform for CPG companies managing Scope 3 supplier emissions in the livestock supply chain. Requirements are machine-readable, typed with unit, threshold, time window, and accepted source. AI pre-reviews evidence; the compliance specialist is reviewer/approver at volume.

01

Evidence Does Not Come from the Supplier

assumption-breaking evidence collection confidence 88% complexity M

The DSL's accepted_sources field for each requirement already encodes who can attest to what. Invert the submission model: Athian queries those authoritative third-party sources directly on a schedule — USDA certification databases, lab testing registries, third-party auditors' APIs — and pre-populates compliance evidence before suppliers are ever prompted. Suppliers confirm or annotate; they do not submit from scratch. The compliance specialist's queue fills with pre-matched evidence, not blank requests.

Basis, rationale & downsides
basis
external: Vanta and Drata both pull evidence from cloud APIs rather than waiting for operators to upload — the architectural lesson is that "accepted sources" typed in the DSL are pull targets, not just validators. Corroborated by the SBOM pattern: once you name what a compliant artifact looks like, tooling emerges to generate and consume it automatically.
rationale
60% of compliance failures originate from third parties (Gartner 2023), yet the current model relies on those same third parties to submit evidence voluntarily. Moving to a pull model means evidence quality depends on Athian's integrations, not supplier diligence. Every new accepted-source integration compounds: each API added improves every requirement that references that source.
downsides
Integration surface is wide — each data source needs a connector. Some sources (small local auditors, paper-based certification bodies) have no API. Supplier expectations shift: they may resist losing control over what gets submitted.
Would we rather build the integration layer once or ask 400 suppliers to figure out how to submit PDFs correctly every year?
compounding_mechanism: "each new buyer's DSL profile makes cross-buyer normalization more precise"
02

Cross-Buyer Requirement Normalization as a Data Flywheel

leverage & compounding standard encoding confidence 90% complexity M

When a supplier manages 15–30 compliance portals simultaneously, most of those requirements overlap — different buyers asking for the same underlying thing in different formats. Because Athian's DSL types every requirement with unit and threshold, the platform can compute when two requirements from different buyers are semantically equivalent. Over time, the accumulated buyer profiles create a requirement graph: one piece of evidence satisfies N requirements across M buyers automatically. This flywheel only works because of the DSL — EcoVadis cannot do it.

Basis, rationale & downsides
basis
external: EcoVadis uses a fixed schema per standard — adding a new standard requires vendor development. That's the constraint; the opportunity is a DSL where requirement equivalence is computable rather than curated. Large suppliers managing 15–30 simultaneous portals have the demand signal: the compliance burden is duplicated across all their buyers, and a platform that collapses it gains direct supplier-side pull independent of any single buyer.
rationale
The flywheel runs on buyer volume: buyer #1 generates no normalization; buyer #50 means the platform has seen most requirement patterns and can pre-match new suppliers' overlaps automatically. The DSL's typed units and thresholds are what make semantic equivalence computable — this is a moat that is structural, not operational.
downsides
Cross-buyer normalization requires enough buyer volume to be useful — it's a slow-start flywheel. Equivalence decisions may be contested by buyers who believe their threshold is meaningfully different from another buyer's superficially similar requirement. Privacy considerations if buyers don't want their requirement language visible to each other.
If we can show a supplier that signing up with Athian collapses their 12-portal burden to one, we've created buyer-independent supplier demand. Does the DSL's type system already support equivalence computation?
compounding_mechanism: "each satisfied control issues a credential; credential value compounds as relying-party count grows"
03

Verifiable Credential Issuance for Satisfied Controls

leverage & compounding supplier experience confidence 88% complexity L

When a supplier satisfies a DSL-typed requirement, Athian issues a W3C Verifiable Credential — a cryptographically signed machine-readable token — attesting to that satisfaction. The VC is portable: any buyer whose requirement maps to the same DSL control can verify it directly without re-auditing the supplier. The supplier proves once; the credential is reused everywhere that control appears. This transforms Athian from a compliance gate into a credential authority, which is a different and more durable market position.

Basis, rationale & downsides
basis
external: W3C Verifiable Credentials standard (VC Data Model 2.0, 2024): a credential issued once is verifiable anywhere without contacting the issuer. The W3C Verifiable Supply Chain Community Group launched February 2026 — the ecosystem formation window is open. SOC 2's shared responsibility model is the operational analog: a vendor's SOC 2 inherits to customers, so compliance propagates through the stack.
rationale
Credential value compounds as the number of relying parties grows — each new buyer who accepts Athian-issued VCs increases the value of every existing credential in the system. The supplier-side demand mirrors the 15–30 portal problem: if a Bovaer adoption credential issued by Athian is accepted by any buyer who requires it, the supplier stops duplicating proof.
downsides
W3C VC infrastructure is still maturing in enterprise supply chains — buyer adoption requires a commitment to accept Athian-issued credentials, which may require commercial agreements. Credential revocation on standard changes needs careful design: a credential for "Bovaer adoption ≥ 90 days" issued under standard v1 may not satisfy standard v2. Complexity is genuinely high.
If we issue VCs today, do we become the verification authority for livestock Scope 3 credentials before anyone else? What does it take to get one buyer to accept them?

04

The Specialist Doesn't Review Suppliers

assumption-breaking review and reporting confidence 85% complexity M

The specialist's job is not to review suppliers — it's to set the quality bar. When DSL types are precise enough, the AI can auto-resolve clean matches: evidence maps to a typed requirement, threshold is met, confidence is high. The specialist reviews only exceptions. Every exception decision becomes a labeled training example: the specialist is teaching the model, not making the same judgment repeatedly. Review time per supplier falls toward zero for clean portfolios; the specialist's attention concentrates on the ambiguous cases where their judgment actually matters.

Basis, rationale & downsides
basis
external: OSCAL machine-readability reduces audit duration from months to minutes by automating the mapping of evidence to controls. Academic accreditation is the structural analog: the accreditor defines outcomes (the DSL), not the path — the specialist's role is outcome verification, not process supervision. reasoned: If a requirement is typed with unit, threshold, and accepted source, the match is binary and automatable. The specialist's judgment is only required at the boundary: evidence that partially satisfies, sources that aren't in the accepted list, threshold edge cases.
rationale
The compliance specialist is the bottleneck at scale. Auto-resolving clean matches removes the bottleneck for the easy cases — which, once the DSL is well-typed, should be the majority. The specialist's queue becomes a curated set of genuine ambiguity, and their decision time becomes training data. Each exceptional decision improves future auto-resolution.
downsides
Liability for auto-resolved decisions — who is responsible when a clean-match auto-resolution turns out wrong? Regulators may require human sign-off on all determinations regardless of confidence. Supplier gaming: once auto-resolution logic is understood, suppliers may optimize for algorithmic match rather than genuine compliance.
If we auto-resolve 80% of requirements, what does the liability structure look like? Does the specialist's sign-off on a batch still count as review?
broken_assumption: "the published standard is the authority for what matters"
05

The Standard Is Not the Source of Truth

assumption-breaking standard lifecycle confidence 78% complexity L

Over time, Athian's cross-customer compliance data reveals what actually predicts emissions outcomes — which thresholds matter, which requirements have low signal-to-noise. That empirical record can function as a parallel benchmark alongside the published standard: not replacing the standard, but annotating it with performance reality. A buyer could choose to weight requirements by predictive validity rather than treating every line item equally. This is the credit-scoring inversion: the standard body defines the schema, but the score is computed from a record, not self-reported.

Basis, rationale & downsides
basis
external: Credit scoring replaces self-attestation with third-party record — the entity being scored does not control the inputs. EcoVadis's fixed schema means it cannot evolve its standard based on outcome data; its schema is the standard body's, not EcoVadis's. Athian, with a DSL that owns the control mapping, has the structural position to annotate requirements with empirical validity — not just compliance status but predictive signal. reasoned: If requirement A has high variance across otherwise-similar suppliers and correlates poorly with actual GHG outcomes, a sophisticated buyer should weight it differently. That's data Athian will accumulate and others won't.
rationale
This is a long-range positioning move. It requires significant data accumulation and outcome validation, but once built it's a durable moat: Athian becomes not just a compliance platform but an empirical authority on what on-farm interventions actually reduce emissions, at scale. The standard body writes requirements; Athian tells you which ones are load-bearing.
downsides
Requires large cross-customer dataset before the signal is meaningful. Standard bodies and buyers may resist a platform that positions itself as a second-order authority on their own standards. Emily's science validation would be load-bearing here — this is a significant scientific and commercial commitment.
Does Emily think the data we'll accumulate is sufficient to say something meaningful about requirement validity? And would any buyer trust that signal over the published standard?
broken_assumption: "the DSL schema is designed by engineers"
06

The DSL Is Not Designed by Engineers

assumption-breaking standard encoding confidence 87% complexity S

Protocol experts like Emily know what a requirement means — the unit, the threshold, the accepted measurement conditions, the exceptions — but cannot currently author a DSL entry without engineering involvement. Invert this: specialists author requirements in structured natural language, and the platform generates the DSL entry. Emily describes a Bovaer adoption requirement in a structured form; the AI produces a typed DSL node; she reviews and approves it. Engineering validates the schema; specialists own the content.

Basis, rationale & downsides
basis
external: NIST OSCAL's catalog layer separates requirement authorship from implementation: the catalog is owned by the standard body, not the compliance system. That separation is what makes OSCAL's reusability work. reasoned: The current design creates a bottleneck where every new protocol update — and Athian is adding protocols regularly — requires an engineering cycle to model the DSL entry. Making that accessible to specialists directly is both a velocity improvement and a quality improvement: the domain expert closest to the requirement's meaning is now writing it.
rationale
This is the lowest-complexity idea in the set — it's a workflow change backed by a natural-language-to-DSL generation layer. The compounding effect is significant: each protocol Emily can update herself is a cycle engineering doesn't spend. As the protocol library grows, the leverage increases.
downsides
AI-generated DSL entries may have subtle errors that domain experts don't catch during review (unit ambiguity, threshold off-by-one). Requires a review workflow where specialists can see and validate the generated DSL, not just the natural language input. Schema validation tooling becomes more critical if the authorship circle widens.
Emily, how often do you wait on engineering to model a protocol change you already understand fully? What would it take for you to own that directly?

07

Standard Change Diff Engine with Auto-Reprofile

leverage & compounding standard lifecycle confidence 87% complexity M

When a standard changes, the DSL's structured representation makes the delta machine-computable: which requirements changed thresholds, which were added, which were removed. The platform can run a diff across all affected supplier plans and surface exactly which suppliers are now out-of-compliance, which are unaffected, and what evidence needs to be collected for newly required controls. Standard updates stop being a manual triage exercise and become a structured remediation queue. The OSCAL catalog → profile → plan separation is what makes this possible — without layer separation, every standard change requires human triage.

Basis, rationale & downsides
basis
external: NIST OSCAL's layer separation (catalog → profile → plan) is explicitly designed to enable re-profiling: a catalog change propagates through profiles to plans in a structured way. The key insight from the OSCAL literature is that separating "what requirements exist" from "which apply here" from "how we satisfy them" is what reduces audit time from months to minutes. Athian's DSL has this structure; the diff engine operationalizes it for the standard-change case.
rationale
CSDDD (July 2029) and emerging Scope 3 reporting mandates will produce multiple standard updates over the next three years. Each one, today, requires manual triage. A diff engine makes Athian the platform that makes standard changes survivable at scale — rather than a source of audit panic, they become a structured remediation workflow. This compounds: each standard update increases the value of being on Athian versus running compliance manually.
downsides
Requires the catalog → profile → plan layer separation to be enforced in the DSL already. If plans are not cleanly separated from profiles, the diff is not automatable. Also requires standards to be in the DSL (not just imported as PDFs) — so this compounds with idea #6 (specialist authorship).
When CSDDD drops a v2 in 2027, what happens to all our existing compliance plans? Does the current DSL structure make that computable or is it still manual triage?
