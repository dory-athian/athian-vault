Ranked Ideas
I1

HANDOFF.md → #ce-handoffs Slack post via Claude Code hook

A3: session continuity Conf 88% Cx Low
Description

Wire a Claude Code PostToolUse hook on the Write tool: when the target path matches HANDOFF.md, send the file's content to Slack via a Slack webhook or the Slack MCP tool. A new #ce-handoffs channel (or #engineering thread) receives the session summary — Active Decisions, Key Files, Next Steps — without anyone going to look for it. Engineers picking up work see what the previous session decided. New engineers on a feature see the full context stack before writing a line.

Basis

direct: HANDOFF.md exists at /Users/doryweiss/Athian/HANDOFF.md and already contains the exact fields that benefit a team member picking up work (Active Decisions, Key Files, Next Steps, Context). The Claude Code hook system supports PostToolUse hooks that fire on specific tool + path combinations — this is the same mechanism that would support ce-commit notifications. The Slack MCP tool is already wired in this session.

Why it matters

Cold-start is the primary failure mode of AI-assisted engineering on a small team. Every new session starts without the previous session's context. Posting HANDOFF.md to Slack makes session continuity an ambient team artifact, not a private document nobody finds. It also makes AI work visible by default — engineers see "Dory's Claude session decided X" in the same channel where they see deployment notifications.

Downsides

HANDOFF.md currently gets written with free-form content — if its structure is inconsistent, the Slack posts will be inconsistent. Requires either standardizing the HANDOFF format (already partially the case) or doing light Claude-side summarization before posting. A #ce-handoffs channel creates a new destination engineers would need to know exists, though routing to an existing channel like #engineering as a thread sidesteps this.

Meeting test

Yes — "do we want CE session summaries showing up in Slack automatically?" is a real team conversation with a clear answer either direction.

I2

Weekly CE digest to Slack — clone of Feedback Hub Slice 5

A4: discoverability Conf 85% Cx Low
Description

An n8n workflow runs every Monday morning. It reads docs/ideation/, docs/plans/, and docs/brainstorms/ (or their git-tracked equivalents once the workspace is git-initialized), collects files created or modified in the past 7 days, sends them to Claude for a structured summary, and posts to #engineering (or #product-engineering): "This week in CE: 2 ideation sessions on compliance DSL, 1 plan for Nestlé POC. Top idea: [title]. Active plan: [plan title] — status [status]." The architecture is identical to Feedback Hub Slice 5, which is already live and tested.

Basis

direct: Feedback Hub Slice 5 is "Built, imported, and end-to-end tested (2026-04-15). Digest quality is strong." (project_feedback_hub.md). The workflow architecture — n8n schedule trigger → read sources → Claude summarization → Slack post — is proven. The CE digest is a structural clone with different source files and a different Claude prompt. No new infrastructure is required.

Why it matters

A weekly digest is the lowest-friction way to make CE work visible across the full team, not just engineers who happen to see individual Slack posts. Product, Sales, and leadership see what's being planned without needing access to the docs directory. It also creates a lightweight accountability signal — if nothing shows up in the digest, the team notices.

Downsides

Requires the CE output files to be accessible to n8n (either via filesystem access, a git remote the n8n machine can reach, or a Google Drive sync). Currently the docs/ directory is local to Dory's machine, so this is blocked until the workspace is git-tracked and pushed to a remote or otherwise shared. Also depends on consistent CE output file creation — a week with no CE work produces a digest with nothing to say.

Meeting test

Yes — "should we get a weekly summary of AI planning work in Slack?" is a clear opt-in/opt-out conversation, and the answer likely yes.

I3

ce-commit hook posts a one-liner to Slack on every CE commit

A5: artifact lifecycle Conf 82% Cx Low
Description

When the ce-commit skill fires (which commits CE planning artifacts to git), wire a PostToolUse hook that posts a single line to Slack: "[ce-commit] Dory committed: Compliance DSL ideation → docs/ideation/2026-06-23-compliance-dsl.html". No summary, no elaboration — just the fact. Engineers see AI-assisted commits the same way they'd see a CI notification. The hook reads the commit message (already formatted by ce-commit) and the file path, formats a Slack message, and fires the Slack MCP tool. Implementation is under 30 lines of hook configuration.

Basis

reasoned: The cultural argument for AI adoption at Athian weights the cultural piece more heavily than the technical piece (CLAUDE.md: "this is a live challenge with both cultural and practical dimensions, and I weight the cultural piece more heavily"). The most direct way to normalize AI-assisted engineering is to make it visible in the team's ambient feed at the moment it happens — not in a weekly digest, not in a special channel, but in the same place where deployment events and PR merges appear. A one-liner has near-zero noise cost and high cultural signal value.

Why it matters

This is the "makes it feel normal" move. AI adoption doesn't compound from mandates — it compounds from visibility, from engineers noticing that AI-assisted work is a routine part of how their colleagues operate. A commit notification does that without any new process.

Downsides

Requires ce-commit to actually be in use (currently it's a skill that exists but may not be consistently used). If CE outputs aren't being committed, the hook never fires. Also: Slack notification volume — if CE commit cadence is high, the feed gets noisy. Mitigation: route to a low-traffic channel or use Slack's thread pattern to keep notifications collapsed.

Meeting test

Yes — "do we want Slack notifications for AI-assisted commits?" surfaces a real team preference about ambient visibility vs. noise.

I4

Plan frontmatter → Linear issue comment on plan creation

A5: artifact lifecycle Conf 80% Cx Low
Description

When ce-plan writes a plan .md file with YAML frontmatter that includes a linear_issue: LIN-123 field, a PostToolUse hook fires the Linear MCP tool to add a comment on that issue: "CE plan written: [plan title] — [2-sentence summary from the plan's abstract]. Full plan: [file path or link]." Engineers who open the Linear issue see the planning artifact that preceded it, directly in the ticket thread. No separate lookup, no separate channel — the artifact surfaces where the work is tracked.

Basis

direct: The Linear MCP server is already wired (docs/solutions/tooling-decisions/linear-mcp-compound-engineering-skills.md confirms the full setup). The Linear MCP's save_comment tool is already available in this session. The docs/solutions file notes that compound-engineering skills "file tickets in whichever issue tracker they detect at runtime" — the reverse direction (plan → issue comment) is the same MCP tool, different direction. Frontmatter discipline is already practiced in docs/solutions/ with module, tags, and problem_type fields.

Why it matters

This closes the loop between planning and execution. A Linear issue that has a CE plan comment is self-documenting — any engineer who picks it up sees the reasoning, the tradeoffs, and the implementation approach without asking anyone. It also makes planning work show up in Linear's activity feed, which is where the Compliance team tracks work.

Downsides

Requires consistent use of linear_issue: in plan frontmatter — if it's missing, the hook doesn't fire. Creating the convention is low friction but depends on the engineer (currently Dory) remembering to add it. Could produce duplicate comments if the hook fires multiple times on the same plan file. Mitigation: check for existing comment with matching title before posting.

Meeting test

Yes — "should planning docs automatically comment on the Linear issue they belong to?" is a concrete team norm question.

I5

Plan frontmatter auto-updates the target repo's CLAUDE.md

A2: CLAUDE.md / context hierarchy Conf 78% Cx Medium
Description

When ce-plan writes a plan with frontmatter declaring repos: [sus-plat], a PostToolUse hook reads the plan's key decisions and appends or updates a "Current Active Plan" block in sus-plat/CLAUDE.md. The block contains: plan title, date, summary (2 sentences), and a link to the full plan file. When Claude Code opens a session in sus-plat, it loads CLAUDE.md and immediately has planning context for the current work — without the engineer manually copying anything. The plan frontmatter is the trigger; CLAUDE.md is the propagation mechanism.

Basis

direct: CLAUDE.md at /Users/doryweiss/Athian/CLAUDE.md already contains rich per-repo context. The docs/solutions file confirms CLAUDE.md is the primary signal that compound-engineering skills read to detect tracker and architecture context. Plans span repos (noted in the focus hint: "platform + sus-plat for Nestlé pilot — cross-repo awareness is a recurring need"). The frontmatter repos: field is already proposed in today's storage ideation — this idea activates it as a propagation trigger rather than just a routing tag.

Why it matters

This is the highest-leverage compounding mechanism: every time a plan is written, it automatically enriches the context for every future Claude Code session in the affected repos. No manual copy-paste. No cold-start. The AI adoption argument compounds because the AI gets better — and visibly so — as CE work accumulates.

Downsides

Medium complexity: the hook needs to write to a different repo's CLAUDE.md, which may be in a separate directory or git repo. Requires the workspace to have write access to the affected repos. The "Current Active Plan" block needs a defined format so subsequent updates replace rather than append indefinitely. Risk of CLAUDE.md bloat if plans aren't cleaned up — needs a "completed" state in frontmatter that triggers removal of the block.

Meeting test

Yes — "should planning context automatically propagate into the repo's CLAUDE.md?" is a meaningful architectural choice about how the team manages AI context.

I6

Running CE index as a Linear Document — auto-appended on file creation

A4: discoverability Conf 75% Cx Low
Description

Maintain a single Linear Document titled "CE Planning Index" in the Athian Compliance team (or a shared workspace). When ce-plan or ce-ideate writes a file, a PostToolUse hook appends one line to the document: "2026-06-23 · [type: ideation] · Compliance DSL — three frames · docs/ideation/2026-06-23-compliance-dsl.html". Engineers who want to find prior CE work open the Linear document — it's a running log, not a search problem. New team members have a single "what has been planned" reference on their first day.

Basis

direct: Linear Documents are persistent, linked to a team, and appear in Linear's sidebar — exactly where Compliance engineers already look. The Linear MCP's save_document tool is available. The Compliance team is the primary user of Linear at Athian (per CLAUDE.md: "Linear (linear.app) for Athian Compliance — piloting a migration from Jira. All new Compliance work is filed in Linear."). Unlike a Slack post (ephemeral) or a file index (requires filesystem access), a Linear Document is discoverable to anyone with Linear access, persists indefinitely, and can be linked from issue descriptions.

Why it matters

Discoverability for CE outputs currently requires knowing to look in docs/ideation/ — a directory that doesn't show up in any tool the team uses. A Linear Document is a persistent, team-visible index that requires no new habit: engineers already have Linear open. It also makes CE work visible to Product (Jess) and Customer Success (Daniel, Chelsea) who may not be in the codebase but are in Linear.

Downsides

A flat log document gets unwieldy past ~50 entries — would benefit from periodic archiving or topic-based organization. Also creates a dependency on the Linear MCP being available in every session where CE outputs are written. The value is cumulative: at 3 entries it looks sparse; at 50 it becomes genuinely useful. Requires consistent use to build the index.

Meeting test

Yes — "should we maintain a shared planning index in Linear?" is a concrete team norm question that Jess and Daniel would have opinions about.
