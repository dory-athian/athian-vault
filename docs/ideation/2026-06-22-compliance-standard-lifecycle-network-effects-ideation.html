Grounding Context

Product: Athian Compliance — AI-native compliance platform for CPG companies managing supplier compliance against shared specs (SQF Code 9.0, retailer private-label requirements). One compliance specialist evaluates many suppliers. Requirements have units, thresholds, and time windows; they expire, renew, and escalate. Evidence arrives heterogeneous: PDFs, certificates, audit reports, lab results.

Internal architecture: DUITA DSL with component-level renderPrompt fields and a confirmed/inferred gap analysis pattern. Platform monorepo backend + sustainability-platform frontend.

Key structural problem: When a standard version updates, every existing supplier evaluation is potentially stale. Approval decisions ("this evidence satisfies this requirement") are siloed per evaluation and never compound. Supplier A certified for Buyer 1 — Buyer 2 needs the same standard; the evidence and rationale already exist but cannot be reused. The multi-buyer platform's overlapping supplier pools are an underexploited network asset.

External grounding: EcoVadis (3M supplier multi-buyer model), NIST OSCAL (machine-readable catalog versioning), W3C Verifiable Credentials 2.0 (2025), GS1 supply chain traceability working group (Feb 2026), EPA Title V permit modification taxonomy, PCAOB AS 2105 materiality thresholds, SOC 2 continuous monitoring patterns.

#1

Standard Version Diff Propagation

Standard lifecycle Conf 91% Cx High external:

When a new standard version is published, the platform computes a machine-readable diff of the DSL encoding (version N vs N+1), classifies each changed clause as BREAKING / MINOR / PATCH, and propagates the impact to all supplier evaluations using that standard — surfacing only the suppliers whose current evidence would fail the new version, before the go-live date. The specialist receives a prioritized burn-down list rather than a full re-audit queue. This is the compliance equivalent of a dependency graph notifying you which packages break when a library upgrades.

Basis
external: NIST OSCAL three-layer model (catalog/profile/plan) directly supports version-diffed machine-readable compliance catalogs; deployed in production to reduce IT audit duration from months to minutes. The aviation AD analogy — applicability rules propagating fleet-wide without human triage — is the structural match for the burn-down prioritization layer.
Why it matters
Standard bodies update major protocols every 3-7 years. Without automated diff propagation, every version update triggers a manual re-audit of every supplier — the compliance equivalent of running npm audit by hand, file by file. Automated propagation converts a project-level effort into a triage queue resolved in hours.
Downsides
Requires DSL encodings of both standard versions to already exist — the platform is dependent on encoding quality and completeness. BREAKING vs MINOR classification for qualitative process clauses requires judgment the DSL encoding must capture in advance.
Meeting test
"When SQF Code 10.0 drops, we want to tell every CPG buyer within 24 hours which of their suppliers need action — and which don't — before any human opens a file."

Directional sketch — DSL diff engine classifies changed clauses; only BREAKING-affected suppliers surface in the specialist queue.

#2

Quantitative Requirement Auto-Disposition

Review & reporting Conf 92% Cx Medium direct:

When a requirement has a structured threshold encoded in the DUITA DSL (e.g., sodium < 800mg/serving, HACCP plan review within 12 months), the platform auto-extracts the value from submitted evidence, computes PASS/FAIL, and routes the evaluation to the specialist only if extraction confidence falls below threshold or the result is FAIL. Clean PASS cases are auto-disposed without human review. The specialist's queue shrinks to the genuinely ambiguous and the genuinely failing.

Basis
direct: DUITA DSL encodes thresholds per requirement component; renderPrompt fields and the confirmed/inferred gap analysis pattern already structure reasoning over evidence against those thresholds. Threshold evaluation is arithmetic once extraction succeeds — the decision logic is already there.
Why it matters
A compliance specialist reviewing a supplier against SQF may evaluate 200+ requirements. A significant fraction are quantitative with determinate thresholds. Auto-disposition of clean passes returns specialist time to the ambiguous qualitative requirements where judgment actually matters — and creates the precondition for Idea 4 (rationale capture compounds only where ambiguity exists).
Downsides
Extraction confidence must be calibrated carefully — false confidence in a PASS is worse than routing to specialist. Requires evidence document quality good enough to reliably extract structured values (lab reports, certs are strong; PDFs with hand-entered tables are weak).
Meeting test
"We want the specialist to open only the cases where a human judgment call is actually necessary — everything with a determinate answer should resolve before they touch it."
#3

Pre-populated Gap Brief

Supplier experience Conf 88% Cx Medium direct:

When a standard version updates, each affected supplier receives a pre-populated gap brief: the specific clauses that changed, the evidence they previously submitted for those clauses, and an AI-generated assessment of whether prior evidence still satisfies the new wording — with explicit gap flagging where it doesn't. The supplier sees exactly what to resubmit and why. They don't receive a new blank compliance checklist; they receive a delta against what they already did.

Basis
direct: DUITA DSL renderPrompt fields and the confirmed/inferred gap analysis pattern are already the infrastructure for generating per-clause gap assessments. Generating a supplier-facing diff brief is a natural extension of what the DSL can already do when applied to version-changed clauses.
Why it matters
Suppliers managing 15-30 compliance portals (PwC 2025) experience version updates as a demand to start from scratch. A pre-populated gap brief converts re-evaluation from a project into a targeted patch. Supplier response time drops; specialist receives targeted evidence rather than a complete resubmission.
Downsides
AI gap assessment quality depends on how well the new version's clause wording is encoded — ambiguous wording in the standard itself makes this unreliable. Risk of false "no gap" assessments that give suppliers false confidence.
Meeting test
"When SQF 10.0 drops, every supplier should know exactly what changed, whether their existing evidence still covers it, and what they need to submit — without opening a compliance document."
#4

Approval Rationale Capture

Review & reporting Conf 87% Cx Low direct:

Every time a specialist marks evidence as satisfying a requirement, the system prompts for a structured rationale — template-guided, 2-3 sentences — capturing why this evidence type, quality level, and scope are sufficient for this clause. Rationales are attached to the requirement clause, versioned alongside the standard, and reused as few-shot examples for AI pre-assessments on future submissions of the same evidence type. The specialist's judgment becomes training data rather than ephemeral workflow.

Basis
direct: DUITA DSL renderPrompt fields provide the infrastructure for structured judgment capture. The confirmed/inferred gap analysis pattern shows the platform already reasons about evidence sufficiency in a structured way — rationale capture surfaces and persists that reasoning.
Why it matters
Currently, specialist judgment is consumed at evaluation time and discarded. Over thousands of decisions, the platform accumulates no institutional knowledge about what evidence quality actually means for each requirement type. Rationale capture converts every approval into a durable signal that improves AI pre-assessment accuracy and makes specialist decisions auditable and explainable.
Downsides
Adds friction to the specialist workflow — rationale prompts must be lightweight enough not to slow review. Risk of rationales becoming perfunctory ("evidence meets requirement") if template quality is low. Requires careful UX design to feel like a useful log, not a compliance tax on the specialist themselves.
Meeting test
"Every specialist decision should teach the system something — right now we're training a person in a room and throwing away the transcript."
#5

Supplier Portable Compliance Record

Supplier experience Conf 85% Cx High external:

Suppliers own their compliance credentials as W3C Verifiable Credentials — the credential is not held by the CPG buyer, it belongs to the supplier. When a supplier enters a new buyer relationship on the platform, their existing validated claims surface automatically, reducing first-evaluation time from weeks to hours. The supplier's compliance history travels with them across buyer relationships rather than being re-collected from scratch by each buyer. This flips the acquisition dynamic: suppliers on the platform bring value to new buyer relationships, making the platform sticky for both sides.

Basis
external: W3C Verifiable Credentials 2.0 published 2025; GS1 supply chain traceability working group using VCs for end-to-end traceability launched February 2026. These are not analogies — they are the active technical substrate for this exact use case in the adjacent supply chain domain.
Why it matters
The current model has no network effect for suppliers: each new buyer relationship re-collects the same evidence from scratch. The portable record converts the supplier into a node in a compliance network rather than a data subject in each buyer's silo — EcoVadis captures 3M suppliers at $1,500-$5,000+/year partly because they aggregate this institutional history. Athian can provide the same benefit without the per-supplier fee friction.
Downsides
Buyers must accept credentials issued under another buyer's evaluation scope — a trust and legal liability question. Credential validity is tied to the standard version under which it was issued; version updates may invalidate or partially invalidate claims. Requires legal framework for credential portability that Athian would need to author.
Meeting test
"A supplier who's already compliant for one of our customers shouldn't have to prove it again for the next — and we should be the platform where that portability lives."
#6

Multi-Buyer Evidence Consent Network

Evidence collection Conf 84% Cx Medium external:

Suppliers opt into a consent framework: evidence validated for Buyer A can be made available to other buyers on the platform evaluating the same supplier against the same standard. When Buyer B opens a new evaluation for a supplier who already has validated evidence on the platform, the relevant evidence surfaces automatically — with consent flags and version provenance clearly attached. Evidence collection effort is divided across buyers rather than duplicated by each.

Basis
external: EcoVadis profiles 3M suppliers at $1,500-$5,000+/supplier/year and allows buyers to access pre-existing supplier ratings — not just raw evidence, but validated assessments. The multi-buyer aggregation model is deployed at scale in supplier sustainability ratings. The consent-gated evidence layer applies the same mechanism at the evidence level rather than the rating level.
Why it matters
82% of compliance teams plan to invest in automation (PwC 2025) — but the current model re-collects evidence from every supplier for every buyer relationship independently. The platform already has overlapping supplier pools across CPG buyers. This is a pure network-effect capture: value compounds as buyer count grows, with no incremental evidence collection cost for shared suppliers.
Downsides
Buyers may have divergent evidence standards for the same requirement — one buyer's "acceptable" lab report may not satisfy another's scope. Competitive sensitivity: buyers may not want competitors to benefit from their evaluation work. Requires careful consent UX and clear data sharing agreements.
Meeting test
"Our suppliers are getting compliance requests from five of our customers for the same SQF clauses — we should be able to stop making them answer the same questions over and over."
#7

Permit-Tier Version Classification

Standard lifecycle Conf 83% Cx Medium external:

When a standard version updates, each changed clause is classified at three tiers — MAJOR, SIGNIFICANT, MINOR — borrowed from EPA Title V permit modification taxonomy. Only MAJOR-classified changes trigger mandatory re-attestation; SIGNIFICANT changes require a targeted re-check against prior evidence; MINOR changes require no supplier action and the existing evidence carries over automatically. This eliminates the false equivalence between an editorial wording change and a threshold tightening — both currently trigger the same full-resubmission response.

Basis
external: EPA Title V permit modification taxonomy (minor/significant/major) is a deployed, legally-established framework for scoping re-permitting obligations to the modified conditions only. The structural fit is precise: both problems require determining which affected parties need to act on which changed regulatory conditions, and at what level of effort.
Why it matters
Standard version updates currently trigger a binary response: full re-evaluation or ignore. A three-tier classification makes re-evaluation scope computable from the classification rather than requiring specialist judgment on every clause update — and provides a defensible audit rationale for why certain prior evidence was carried over.
Downsides
Classification must be authored per clause per version update — unless the DSL diff engine (Idea 1) computes it automatically. If manual, this is a labor-intensive encoding task. The MAJOR/SIGNIFICANT/MINOR taxonomy may not map cleanly to food safety regulatory norms.
Meeting test
"We can't treat every word change in SQF as a full re-audit trigger — we need a defensible way to scope what actually requires new evidence."
#8

Materiality-Weighted Review Routing

Review & reporting Conf 82% Cx Medium external:

Each requirement clause is assigned a risk weight based on food safety criticality and regulatory exposure. Evidence for high-weight clauses receives substantive specialist review. Evidence for low-weight clauses receives AI-only analytical review unless the AI flags an anomaly. The specialist's time is allocated proportionally to risk — the same model PCAOB AS 2105 uses to justify differential audit procedures for material vs non-material line items.

Basis
external: PCAOB AS 2105 proportionality framework: substantive evidence review above materiality threshold, analytical review procedures below. Deployed in public company auditing; the methodology is legally defensible and well-documented. The CPG compliance analogue: food safety criticality and regulatory exposure as materiality proxies.
Why it matters
Without risk-weighted routing, a specialist reviewing 200 requirements allocates equal time to a HACCP critical control point and a supplier record retention policy. Risk weighting multiplies specialist capacity without adding headcount — and the PCAOB analogy provides an audit-defensible methodology for why AI-only review was applied to low-risk clauses.
Downsides
Risk weights must be authored and maintained — who decides, and what's the basis? CPG buyers may have divergent risk models. An incorrect low-risk classification for a clause that later becomes a regulatory focus creates liability exposure.
Meeting test
"We need a defensible way to say 'we applied human review where it mattered and AI review where it didn't' — right now we can't say that."
#9

Requirement-Clause Semantic Versioning

Standard encoding Conf 80% Cx Medium external: + reasoned:

Each requirement clause in the DSL encoding carries a semantic version tag at the clause level: BREAKING (evidence structure changes, threshold tightens, or new evidence type required — re-evaluation mandatory), MINOR (wording change, same intent, same evidence structure — AI re-check only), or PATCH (editorial change — no supplier action). This makes "does this change break my supplier's compliance?" computable from the clause tag alone, without requiring specialist judgment on each updated clause.

Basis
external: Software semantic versioning (semver) — BREAKING/MINOR/PATCH classifies whether an upgrade is backward-compatible. The structural fit is precise: both problems require determining whether a downstream consumer (a package / a supplier evaluation) needs to change behavior when an upstream dependency (a library / a standard clause) updates. reasoned: For quantitative clauses with thresholds, BREAKING vs MINOR is arithmetic (threshold delta). For qualitative clauses, it requires encoding judgment at authoring time — feasible for known standards, harder for novel ones.
Why it matters
This is the encoding infrastructure that Idea 1 (Diff Propagation) and Idea 7 (Permit-Tier Classification) both depend on. Building it as a first-class DSL concept rather than inferring it at evaluation time makes version propagation fully computable and auditable — the classification lives in the standard encoding, not in ad-hoc specialist judgment at update time.
Downsides
Classification must be authored at DSL encoding time — the quality of version propagation is limited by the quality of the semver tags. Qualitative clauses require encoding judgment that may itself require specialist review.
Meeting test
"We want to be able to look at any two versions of SQF and know — computationally, not by reading every clause — which changes are breaking for which suppliers."
#10

Process vs Outcome Requirement Distinction

Standard encoding Conf 79% Cx Low external:

The DSL encoding distinguishes two requirement types that SQF conflates in its human-readable document: process requirements (was the training conducted, was the SOP followed, was the review performed?) and outcome requirements (did the test result meet the numeric threshold?). These have fundamentally different evidence structures, evidence source types, expiry logic, and AI extraction approaches. Currently, the platform treats them identically — limiting automation and making version-change classification harder.

Basis
external: McDonald's and Hilton franchise brand standards operations audit frameworks explicitly distinguish process requirements (training logs, operational checklists, procedural SOPs) from outcome requirements (mystery shopper scores, measurable product specs). These have different evidence structures, accepted-source definitions, and audit sampling approaches — the franchise industry developed this distinction because conflating them produces broken audit logic for the process side.
Why it matters
Auto-disposition (Idea 2) and materiality weighting (Idea 8) both behave differently for process vs outcome requirements. Without the distinction, the DSL is missing a load-bearing structural fact about SQF requirements — and version-change classification becomes harder because a threshold change in an outcome requirement is clearly BREAKING while a frequency change in a process requirement may be MINOR or MAJOR depending on the process type.
Downsides
Requires re-encoding existing DSL entries to carry the type tag — a one-time migration cost for each standard in the catalog. Some clauses are genuinely hybrid (a process requirement with an outcome threshold embedded) and may require human judgment to classify.
Meeting test
"A training record and a lab result are not the same kind of evidence — our DSL shouldn't pretend they are."
#11

Policy-Authored Specialist Architecture

Review & reporting Conf 78% Cx High reasoned:

The constraint flip: instead of a specialist reviewing every submission, the specialist authors policies — structured rules like "any ISO 22000 certificate issued by an accredited body within the last 24 months is auto-approved for clauses 2.1.1 through 2.1.4" — and the platform applies them at scale. Specialist review is reserved for submissions that no policy covers (novel evidence types, edge cases, ambiguous scope). The specialist's job shifts from reviewer to policy author and exception handler.

Basis
reasoned: The constraint flip — fixed specialist headcount, unbounded supplier volume — is the forcing function used in fraud detection, content moderation at scale, and rules-based underwriting. In each domain, human judgment is captured as policy rather than exercised per-case. The DUITA DSL already encodes requirement structure; policy authoring is the natural next layer, turning specialist judgment into a reusable execution rule rather than a per-submission event.
Why it matters
At current scale, specialist headcount must grow with supplier volume. The policy-authored architecture decouples them: one specialist's policy covers thousands of equivalent cases. This is the architectural move that makes the platform viable at enterprise CPG scale — the difference between a compliance review tool and a compliance operating system.
Downsides
Policy authoring is a new UX surface that doesn't exist yet — designing it well enough that specialists can write reliable rules (rather than over-broad or over-narrow ones) is a hard product problem. Policy conflicts and edge cases require careful resolution logic. A bad policy applied at scale causes systematic errors.
Meeting test
"We should never need to hire a compliance specialist just because we added 100 suppliers — one specialist's judgment should be able to cover 10,000 submissions."
#12

Applicability Rules Engine

Standard lifecycle Conf 77% Cx Medium external:

Each requirement clause in the DSL carries applicability rules: the facility types, production volume ranges, and product categories for which the clause applies. When a new standard version publishes or a new supplier is evaluated, the applicability rules engine evaluates which clauses actually apply to that supplier before any evidence review begins. Suppliers are never presented with requirements that don't apply to their facility type — and version updates that change applicability rules (not just clause wording) are automatically handled.

Basis
external: Aviation Airworthiness Directives — the FAA encodes applicability rules per AD (aircraft type, engine model, serial number range). When an AD is issued, the system evaluates which registered aircraft are in-scope without human triage. The structural fit: both problems require matching a changed regulatory requirement against a population of affected entities using structured applicability metadata.
Why it matters
Without an applicability engine, version-delta burn-downs (Idea 1) generate false positives: suppliers flagged for clauses that don't apply to their facility type. The applicability layer is the filter that makes the burn-down list credible. It also prevents the specialist from wasting review time on inapplicable clauses.
Downsides
Applicability rules must be encoded per clause — this is encoding labor that must happen before the engine provides value. Supplier facility metadata must be accurate and current; stale metadata produces incorrect applicability determinations.
Meeting test
"We shouldn't be asking a small pasture-based producer to respond to a requirement written for a 50,000-head feedlot operation — the system should know the difference before it asks."

Rejection Summary

Idea Reason Rejected
Evidence Passport (I-02) Weaker formulation of #5 (Supplier Portable Compliance Record). Doesn't address buyer trust and legal liability for third-party-issued credentials; AC-006 does.
Live Compliance State (I-04) Evidence ingestion precondition unresolved. SOC 2 continuous monitoring works because evidence is machine-readable and auto-collected; food/ag compliance evidence is heterogeneous and human-submitted. Analogy stretches past its breaking point.
Standard Bodies as Encoding Partners (I-05) Business development bet, not a product mechanism. The DSL moat argument proves encoding has value; it doesn't support co-publishing as an achievable outcome. Standard bodies are slow-moving with existing IP concerns.
Version-Scoped Compliance History (I-06) The mechanism (attach evaluations to standard version at assessment time) is subsumed by Idea 1 (Diff Propagation), which builds version history as a byproduct of its core functionality.
Evidence Provenance Graph (LC-03) Cross-buyer evidence reuse requires buyers to accept evidence validated under a competitor's evaluation. Consent and competitive sensitivity unresolved. Idea 6 (Multi-Buyer Evidence Consent Network) handles this more rigorously with the EcoVadis basis.
Specialist Decision Corpus (LC-04) Too vague — "ML flywheel" reasoning applies to every domain. No mechanism for how the corpus is used, no external anchor, no argument for Athian-specificity. The compounding benefit is partially captured by Idea 4 (Rationale Capture) with a direct basis.
Tax Code Grandfathering Rules (CD-06) Analogy is imprecise: IRS grandfathering windows are set by statute, not computed from evidence strength. Who sets the grandfathering window in compliance and by what authority is unresolved. Idea 7 (Permit-Tier Classification) covers the same scope-limiting territory more rigorously.
Compliance Delta Budget (AC-002) Underspecified preconditions. Requires a working evidence quality scoring model not yet established. Conflates evidence quality assessment with version impact tolerance without resolving either. Overlaps with LC-02 (Semantic Versioning) without adding a sound mechanism.
Continuous Compliance Signal with Drift Detection (AC-007) Same evidence ingestion problem as I-04. "Standard version proximity" signal is interesting but draft publication timelines are not machine-readable for most standards bodies. Describes a desirable end state without resolving the preconditions.
